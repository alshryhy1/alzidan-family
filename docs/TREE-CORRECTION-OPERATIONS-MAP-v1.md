# Tree Correction Operations Map v1

**الحالة:** مرجع فتح تنفيذ (اتجاه معتمد) · **ليس** migration · لا كود حتى عبارة فتح صريحة  
**التاريخ:** 2026-08-15  
**آخر تحديث:** نطاق التنفيذ الحالي — ويب مصدرًا؛ إدارة+مندوب استقبالًا؛ الجوال خارج الشريحة  
**العبارة:** نوقف ترقيع `tree_card`؛ نبني محرك تصحيح متعدد المسارات بعقد موحّد  
**المراجع:** [`REQUEST-CATALOG.md`](./REQUEST-CATALOG.md) · [`PERSON-VISIBILITY-SPEC-v1.md`](./PERSON-VISIBILITY-SPEC-v1.md) · [`ENGINEERING-ROADMAP.md`](./ENGINEERING-ROADMAP.md) §Tree Engine v2 · تدقيق المرسل↔المستقبل (2026-08-15)

## 0) القرار الأحمر

1. **لا محرر بطاقة شجرة عام** لكل طلب تصحيح.
2. **لا زر «حفظ» عام** — كل عملية تعرف ماذا تغيّر وعلى من وبأي مسار تحقق.
3. **`tree_card` = إضافة فرد فقط** — ليست «أي شيء متعلق بالشجرة». **العملية تحدد النوع؛ نوع البيانات لا يحدد العملية.**
4. النية في الفهرس تبقى **«صحح بيانات»**؛ تحتها **`operation`** واضح.
5. الأسماء التقنية مفاهيمية — **لا أعمدة DB** قبل مراجعة schema حيّة وفتح تنفيذ.
6. أي عملية تلمس النساء/العرض تلتزم [`PERSON-VISIBILITY-SPEC-v1.md`](./PERSON-VISIBILITY-SPEC-v1.md).
7. لا اختراع `person_id` / `parent_person_id` من الاسم وحده — تطابق غامض = `needs_review`.
8. كل عملية خطيرة = **معاينة أثر (ما يتغير + ما لا يتغير) → موافقة → حفظ → سجل**.
9. **Cross-Client Contract (§0.1)** + **تحقق عند الإنشاء والاستقبال (§0.2)**.
10. **قاعدة الحفظ الحاكمة:** لا حفظ يغيّر غير ما عاينته الإدارة ووافقت عليه.

## 0.1) Cross-Client Contract Rule — ملزم

> كل عملية تصحيح أو تعديل يمكن إنشاؤها من التطبيق يجب أن يكون لها **عقد canonical واحد** تشترك فيه **التطبيق** و**الويب** و**الإدارة**. لا يجوز لأي عميل إنشاء صيغة خاصة به لنفس العملية، ولا يجوز للإدارة تفسير نص حر لتحديد العملية إذا كان يمكن إرسال نوع العملية وبياناتها المنظمة.

> عند تطوير تحسين لمسار قائم، تتم مراجعة **المرسل والمستقبل ومسار الحفظ** معًا، وليس تعديل الطرف المتأثر فقط.

```text
Mobile / Web
      ↓
Correction Contract  (operation + canonical payload)
      ↓
Server-side validation   ← إلزامي؛ لا يكفي التزام الواجهة
      ↓
approval_requests
      ↓
Admin Router
      ↓
محرر العملية الصحيح
      ↓
Validation + Preview (ما يتغير / ما لا يتغير)
      ↓
مسار الحفظ الصحيح
      ↓
الشجرة / الهوية
```

### ما يُمنع

| ممنوع | السبب |
|-------|--------|
| جوال بنص حر لنفس عملية لها payload منظّم على الويب | يعيد التصنيف الخاطئ |
| ويب بعقد مختلف عن الجوال لنفس `operation` | إدارتان ضمنيًا |
| إصلاح الإدارة فقط والمرسل قديم | تحسين غير مكتمل |
| استنتاج `operation` من النص عند وجود حقل منظم | هش |
| اكتمال مسار عميل واحد فقط | يكسر العقد الموحّد |
| عميل قديم يُدرج payload غير صالح دون رفض | طلبات مشوّهة في الطابور |

### اختبارات القبول

**عالميًا (عند اكتمال العملية لكل العملاء المعتمدين):**

```text
Mobile → Request → Admin/Delegate → Preview → Save → Tree
Web    → Request → Admin/Delegate → Preview → Save → Tree
Legacy → Safe Recovery/Review → no wrong reinterpretation
```

**شريحة التنفيذ الحالية (§8):** يكفي  
`Web → Admin/Delegate → reorder_children → Preview → Save → Tree`  
+ Legacy. الجوال **خارج النطاق** حتى فتح صريح لاحقًا.

## 0.2) تحقق العقد عند الإنشاء والاستقبال — ملزم

> العقد يُتحقق منه عند **الإنشاء** وعند **الاستقبال**، وليس عند الواجهة فقط.

- إصدار جوال قديم بعد أشهر **لا يجوز** أن يمرّر payload غير صالح إلى `approval_requests` كطلب «سليم».
- الرفض عند الإنشاء برسالة واضحة؛ والصفوف التي تفلت (تراث/يدوي) تُصنَّف عند الاستقبال: `needs_review` / `unsupported` — **بلا تفسير تلقائي خاطئ**.

## 0.3) فصل الأنواع عن «كل ما يخص الشجرة» — ملزم

| المفهوم | المعنى |
|---------|--------|
| `tree_card` | **إضافة شخص / بطاقة إضافة فرد** فقط |
| `tree_edit` | تعديل فرد قائم بالمسار المتوافق الحالي (إلى أن يُغلف تحت عمليات أوضح) |

| `phone_link` | ربط جوال غير مرتبط بشخص موجود |
| `phone_duplicate_conflict` | جوال مرتبط بشخص آخر → تعارض هوية |
| … | كل عملية في §2 |

**ممنوع مستقبلًا:** «هذا متعلق بالشجرة → `tree_card`».

## 1) النموذج المفاهيمي للطلب

```text
request
├── intent          → صحح بيانات (كتالوج)
├── kind            → tree_edit | tree_correction (لاحقًا) | tree_card فقط للإضافة
├── operation       → انظر §2
├── targets         → person_ids[] / parent_person_id / branch_key
├── match_inputs    → أسماء / جوالات للمطابقة فقط (ليست مرجع التنفيذ)
├── requested_changes
├── source          → web_rx | mobile | delegate | admin | legacy
└── review_state    → complete | needs_review | unsupported | conflict
```

النص البشري للعرض والتدقيق؛ **مصدر التنفيذ** = `operation` + أهداف بالهوية + التغييرات المعاينة.

## 2) سجل العمليات (Operation Registry)

| # | العملية | `operation` | النطاق | مرسل اليوم | مرجع التنفيذ (canonical) | واجهة الإدارة | مسار الحفظ | تحقق قبل الحفظ | عند الفشل |
|---|---------|-------------|--------|------------|---------------------------|---------------|------------|----------------|-----------|
| 1 | تغيير الأب / ابن تحت أب خطأ | `parent_change` | علاقة | نص حر فقط | `person_id`, `new_parent_person_id` (+ قديم اختياري) | محرر علاقة + أثر | Tree Engine نقل أب | أب فريد؛ لا غموض | `needs_review` |
| 2 | ترتيب الأبناء | `reorder_children` | مجموعة تحت أب | **لا** (الطلب الحالي دخل نصًا خاطئًا) | `parent_person_id` + `ordered_children: person_id[]` بعد مطابقة آمنة | محرر مجموعة | تحديث `birth_order` دفعة | الكل تحت نفس الأب؛ مطابقة كاملة أو مراجعة | لا تخمين؛ لا ترتيب جزئي صامت |
| 3 | تصحيح جوال شخص معروف | `phone_correction` | شخص | جزئي عبر `tree_edit` | `person_id`, `phone_new`, `phone_old?` | محرر جوال (تصحيح) | تحديث ربط الهاتف | تنسيق؛ الرقم غير لشخص آخر | تعارض → `phone_duplicate_conflict` |
| 4 | ربط جوال غير مرتبط بشخص | `phone_link` | شخص↔جوال | لا | `person_id`, `phone` | محرر جوال (ربط) | ربط هوية | الشخص موجود؛ الرقم حر | مراجعة |
| 5 | تعارض جوال مع شخص آخر | `phone_duplicate_conflict` | هوية | لا | `phone`, `claimed_person_id?`, `existing_person_id` | محرر تعارض / مراجعة | لا حفظ صامت؛ قرار صريح | إظهار الطرفين | إيقاف حتى الحسم |
| 6 | إضافة شخص تحت أب | `add_person` | فرد | RX / جوال / `tree_card` | حمولة `tree_card.v1` | مسار **إضافة فرد** (ليس Router تصحيح) | import/upsert | TREE-003؛ حارس تكرار | رفض الاعتماد |
| 7 | تصحيح اسم | `name_correction` | شخص | `tree_edit` | `person_id`, `name_new` | محرر شخص | تحديث اسم | لا دمج صامت | مراجعة إن التباس |
| 8 | تصحيح حقول أب/أم (عرض) | `parent_fields_correction` | شخص+عرض | لا | أهداف + حقول مسموحة | محرر شخص + Visibility | حقول مصرّح بها فقط | لا إظهار محظور؛ لا اختراع علاقة | إيقاف |
| 9 | نقل شخص بين أبوين | `move_person` | شخص+علاقة | أدوات مباشرة فقط | `person_id`, `from_parent_id`, `to_parent_id` | محرر علاقة + أثر | Move UUID | Dry-run | إيقاف |
| 10 | تصحيح مجموعة أبناء | `group_correction` | مجموعة | لا | `parent_person_id` + تغييرات لكل `person_id` | محرر مجموعة | بعد حسم كل عنصر | عملية فرعية صريحة لكل صف | العناصر غير المحسومة تبقى مفتوحة |
| 11 | إضافة مجموعة (أرقام/أسماء) | `add_children_group` | مجموعة | لا كطلب موحّد | بعد المطابقة: قرارات per-row | جدول مطابقة ثم إجراءات | ربط و/أو إنشاء حسب الحالة | **لا «حفظ المجموعة» الواحد** حتى تُحسم كل الحالات | تعارض/غير صالح يوقف الإغلاق |
| 12 | تصحيح فرع | `branch_correction` | شخص | تعديل فرع الطلب فقط | `person_id`, `branch_key_new` | محرر شخص/علاقة | نقل فرع آمن | اتساق الأب/الفرع | مراجعة |
| 13 | دمج/تعارض هوية | `identity_merge_review` | شخصان+ | حارس يمنع | `person_ids[]`, قرار | مسار دمج | dry-run | لا دمج تلقائي | موافقة صريحة |
| 14 | تصحيح مسار نسب | `lineage_path_correction` | سلسلة | لا | آباء بالـUUID | محرر مسار + أثر | سلسلة عبر UUID | لا بناء من أسماء فقط | مراجعة |

**مرشّح لاحقًا:** زوجة/أم · مولود · وفاة مرتبطة · فصل مكرر · إصلاح `parent_person_id` الناقص — بنفس السجل.

## 2.1) `reorder_children` — تعريف أدق

| طبقة | الدور |
|------|--------|
| مدخلات المندوب (أسماء / أرقام ترتيب) | **للمطابقة فقط** |
| بعد مطابقة آمنة | `parent_person_id` + `ordered_children: [person_id, …]` |
| مرجع الحفظ | **الهوية فقط** — ليس الاسم |
| فشل مطابقة أي فرد | `needs_review` — **لا تخمين** |

---

## 2.2) عمليات الجوال — ثلاثة مسارات منفصلة

| عملية | متى | محرر |
|-------|-----|------|
| `phone_correction` | شخص معروف؛ تغيير رقمه | تصحيح جوال |
| `phone_link` | رقم حر → ربط بشخص موجود | ربط |
| `phone_duplicate_conflict` | الرقم لشخص آخر | تعارض — لا يمرّ بمحرر التصحيح العادي |

---

## 2.3) إضافة/تصحيح مجموعة — مطابقة قبل أي حفظ

مثال 10 أرقام:

| نتيجة المطابقة | الإجراء |
|----------------|--------|
| موجود تحت الأب / قابل للربط | جاهز للربط (بعد موافقة) |
| غير موجود | يحتاج إنشاء (قرار صريح) |
| مرتبط بشخص آخر | تعارض — لا يُغلق الطلب |
| غير صالح | مراجعة — لا يُغلق الطلب |

> العملية الجماعية **لا تُغلق** حتى تُحسم كل الصفوف. ممنوع «حفظ المجموعة» دفعة عمياء.

## 3) موجّه الإدارة (Router)

```text
طلب تصحيح
    │
 تثبيت operation (من العقد — لا من تفسير النص)
    │
┌───────────┼───────────┐
↓           ↓           ↓
شخص      مجموعة      علاقة/هوية
    │           │           │
    └───────────┼───────────┘
                ↓
    Preview: ما يتغير + ما لن يتغير
                ↓
         تحقق نهائي
                ↓
         مسار الحفظ = نفس الأثر المعاين
                ↓
         سجل العملية
```

| عائلة | عمليات |
|-------|--------|
| محرر شخص | `name_correction`, `parent_fields_correction`, `branch_correction` |
| محرر جوال | `phone_correction` · `phone_link` · `phone_duplicate_conflict` (شاشات منفصلة) |
| محرر مجموعة | `reorder_children`, `group_correction`, `add_children_group` |
| محرر علاقة | `parent_change`, `move_person`, `lineage_path_correction` |
| مراجعة هوية | `identity_merge_review` |
| إضافة فرد | `add_person` / `tree_card` — **خارج Router التصحيح كافتراضي** |

## 4) معاينة الأثر + «ما لن يتغير» — ملزم

كل Preview يعرض قسمين:

1. **يتغير:** …  
2. **لن يتغير:** …

| عملية | يتغير (حد أدنى) | لن يتغير (مثال إلزامي) |
|-------|------------------|-------------------------|
| `reorder_children` | ترتيب الأبناء تحت الأب فقط | الأسماء، الجوالات، تواريخ الميلاد، الآباء، الهويات |
| `parent_change` / `move_person` | علاقة الأب، مسار نسب، فرع مستنتج إن لزم | حقول غير معروضة في المعاينة |
| `phone_correction` | الجوال | الاسم، الأب، الترتيب، الميلاد ما لم يُعاين |
| `add_children_group` | حسب قرارات الصفوف المحسومة فقط | لا إنشاء/ربط لصفوف غير محسومة |
| `name_correction` | الاسم | الجوال/الأب ما لم يُعاين |
| `identity_merge_review` | روابط الدمج المعاينة | لا دمج صامت لطرف غير معروض |

**قاعدة الحفظ:** مسار الحفظ ينفّذ **نفس الأثر المعاين فقط** — لا تسريب تعديلات جانبية من محرر عام.

## 5) المرسل اليوم ↔ الفجوة

| مصدر | اليوم | فجوة التصحيح الجماعي/الترتيب |
|------|-------|------------------------------|
| RX ويب | `tree_edit` فرد | لا `reorder_children` |
| جوال ≥ 2026-08-12 | `tree_edit` | نفس الفجوة |
| جوال قديم | نص تصحيح + `tree_card` | الطلب الحالي — مسار خاطئ |
| مندوب | كتابة مباشرة + قبول طلبات | قبول `tree_edit` بلا تطبيق شجرة |
| إدارة | تعديل كامل لـ `tree_card` | لا Router عمليات |

## 6) الطلب الحالي (لاحم — ترتيب أسماء)

| | |
|--|--|
| ليس `tree_card` | نية ترتيب/تصحيح مجموعة |
| لا يُحفظ بالواجهة الحالية | محرر إضافة فرد = أداة خاطئة |
| المسار الصحيح | مطابقة → `reorder_children` بالـ`person_id` → Preview (ترتيب فقط) → حفظ |
| بلا مطابقة آمنة | `needs_review` — لا تخمين |
| إعادة JSON بطاقة | **ممنوع** |

## 7) سياسة الصفوف القديمة + اختبار Legacy

| صنف | إجراء لاحق |
|-----|------------|
| `tree_card` + نص «طلب تصحيح بيانات من تطبيق…» | عرض/تصنيف كتصحيح؛ لا import ابن |
| `tree_edit` بلا منفّذ | Router أو مراجعة يدوية صريحة |
| `tree_card` canonical | مسار إضافة الفرد |
| ترتيب أسماء بلا أب/هويات | `needs_review` |

إصلاح الأرشيف: تشخيص → idempotent → **لا UPDATE أعمى** · **لا إعادة تفسير تلقائي خاطئ**.

### اختبار قبول ثالث — إلزامي

```text
Legacy Request
      ↓
Classification
      ↓
Safe Recovery / Review
      ↓
Admin
      ↓
NO automatic reinterpretation as tree_card apply
```

الهدف: **القديم لا ينهار، والجديد لا يُفسَّر خطأ.**

## 8) نطاق التنفيذ الحالي — معتمد

### السلسلة المعتمدة لهذه الشريحة

```text
المصدر الرئيسي: الويب
      ↓
إنشاء طلب التصحيح (Correction Contract)
      ↓
approval_requests
      ↓
الاستقبال: الإدارة + المناديب
      ↓
Correction Router
      ↓
المحرر المناسب للعملية
      ↓
Preview (ما يتغير / ما لن يتغير)
      ↓
الحفظ في مسار الشجرة الصحيح
```

### أدوار الأطراف

| الطرف | دوره في هذا التنفيذ |
|-------|---------------------|
| **الويب** | المصدر الرئيسي لإنشاء طلبات التصحيح |
| **الإدارة** | استقبال، تصنيف، مراجعة، معاينة، حفظ |
| **المناديب** | استقبال/تنفيذ **المسار المخصص لهم** حسب نوع الطلب والصلاحية — بنفس العقد؛ ليسوا نسخة مصغّرة من الإدارة ولا يعيدون كتابة الطلب كنص حر |
| **الجوال** | **خارج هذا التنفيذ** — لا تعديل عليه الآن |

### اختبار القبول لهذه الشريحة

```text
Web → Admin/Delegate (حسب الصلاحية) → reorder_children → Preview → Save → Tree
```

+ اختبار Legacy → Safe Review (بلا إعادة تفسير كـ `tree_card` apply).

**Mobile → … غير مطلوب لإغلاق هذه الشريحة.** يُفتح لاحقًا عندما يأتي تحسين يحتاجه — مع العودة لقاعدة Cross-Client قبل اعتبار العملية مكتملة عالميًا.

### قاعدة المندوب في هذه الشريحة

- إن كانت العملية من صلاحية المندوب: يصل بـ `operation` + بيانات منظمة، وينفّذ/يحيل عبر **نفس العقد**.
- ممنوع أن يتحول طلب منظم عند المندوب إلى «نص جديد» يُعاد إدخاله.
- من يستلم (`Admin` vs `Delegate`) يُحدَّد بالصلاحية ونوع العملية — لا بتخمين من الرسالة.

### ما يتوقف / أول شريحة عند الفتح

**يتوقف الآن**

- ترقيع «تعديل كامل» لكل التصحيحات.
- قبول `tree_edit` = تطبيق شجرة ضمني.
- إنشاء تصحيح جديد تحت `tree_card`.
- إصلاح طرف واحد فقط لنفس العملية.
- إدخال الجوال في نطاق هذه الشريحة.

**أول شريحة تنفيذ (بعد عبارة فتح صريحة)**

1. Correction Contract + **تحقق خادم** عند الإنشاء/الاستقبال (مسار الويب).
2. Admin Router + مسار مندوب عند الصلاحية + `reorder_children` (هويات بعد مطابقة) + Preview يتغير/لا يتغير.
3. مرسل **Web** بنفس العقد.
4. مسار الحفظ = أثر المعاينة فقط.
5. اختبارات: Web→Admin/Delegate→Tree · Legacy→Safe Review.
6. لاحقًا: `parent_change` / مسارات الجوال / `add_children_group` · ثم Mobile عند الحاجة مع عقد موحّد.

**لا يبدأ مع الشريحة الأولى**

- تعديل تطبيق الجوال · DW · أعمدة schema بلا مراجعة حية · Wireframe منفصل عن هذا السجل.

## 9) معيار النجاح (هذه الشريحة)

- طلب التصحيح من **الويب** يصل بـ `operation` أو `needs_review`/`unsupported` بسبب صريح.
- الإدارة (والمندوب عند الصلاحية) لا تفتح أداة لا تخص العملية.
- **لا حفظ يغيّر غير ما عاينته الجهة المنفّذة.**
- `tree_card` للإضافة فقط؛ التصحيح لا يُخفى داخله.
- المندوب لا يعيد كتابة طلب منظم كنص حر.
- اختبار Web→Admin/Delegate→Tree ناجح؛ Legacy→Safe Review ناجح.
- **عدم** اشتراط Mobile لإغلاق هذه الشريحة؛ عند فتح Mobile لاحقًا يُعاد Cross-Client كاملًا قبل إعلان الاكتمال العالمي.
- المجموعة لا تُغلق وفيها صف تعارض/غير صالح/غير مطابق.
