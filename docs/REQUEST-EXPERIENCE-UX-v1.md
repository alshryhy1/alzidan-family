## 1) الغرض والتموضع

### 1.1 ماذا هي Request Experience؟

واجهة الزائر (والمسار التشغيلي المخصّص لسر المندوب في الإدارة) تجيب عن سؤال واحد:

> **ماذا تريد أن تفعل؟**

الزائر يختار **نية بشرية** من الفهرس، يملأ **حقائق قصيرة** تكفي لتحديد النية، يرى **ما فهمه النظام** ويؤكّده، **يرسل طلبًا للمراجعة**، ثم **يتابع** حالته بلغة الشحن البشرية — دون بناء الشجرة ودون مصطلحات قاعدة بيانات.

### 1.2 ماذا ليست؟

| ليست | لأن |
|------|-----|
| محرّر شجرة / نسب متداخل | النظام يبني الربط بعد الاعتماد — الزائر يقدّم حقائق ويرسل طلبًا |
| Validation Engine | RX تجمع وتعرض — لا تعيد اختراع فحوصات الأعمال |
| Workflow Engine | RX لا تملك الحالات ولا التعيين |
| Delegate Workspace | مساحة المندوب مرحلة لاحقة · UX منفصل معتمد |
| لوحة «اختر نوع البطاقة» | لغة محظورة — النية فعل بشري |
| زر «حفظ في الشجرة» | Single Write — المستخدم يرسل طلبًا فقط |
| توسعة فهرس مرشّح | زوجة/أبناء/ميلاد بلا صف فهرس = لا شاشة في v1 |

### 1.3 الطبقة في المعمارية

```
الزائر
   │
   ▼
Request Experience     ← نية · حقائق · تأكيد فهم · إرسال طلب · تتبع إنساني
   │ يسلّم حقائق
   ▼
Validation Engine      ← يتحقق — لا ينفّذ
   │
   ▼
Workflow Engine        ← حالة · مالك · Audit · إشعار
   │
   ▼
(… مندوب / إدارة / خدمات عند applied)
```

**قاعدة الطبقة (أ):** كل عنصر في RX = طبقة Request Experience فقط.  
أي منطق تحقق أعمال أو انتقال حالة داخل الواجهة = **رفض تصميم**.

## 2) مبادئ التصميم (غير قابلة للتفاوض)

| # | المبدأ | المعنى في RX |
|---|--------|--------------|
| 1 | **Human First** | أفعال عربية من [`PRODUCT-LANGUAGE.md`](./PRODUCT-LANGUAGE.md) فقط |
| 2 | **نية أولًا** | الشاشة الأولى = «ماذا تريد أن تفعل؟» لا نموذج طويل |
| 3 | **نماذج قصيرة** | أقل حقول لازمة لتحديد النية — الباقي يبنيه النظام / VE / المندوب **بعد** التحديد الواضح |
| 4 | **No Database Thinking** | ممنوع: JSON · Parent · `tree_card` كعنوان · نسب جد١…٤ دفعة واحدة كلغة أساسية |
| 5 | **Single Write Rule** | RX لا تكتب على `tree_*` / أحداث معتمدة / memory / cards خارج مسار الطلب — انظر §2.2 |
| 6 | **Truth Before Speed** | عند فشل VE أو غموض هوية: رسالة بشرية + تحديد/تعديل — لا «إرسال رغم الخطأ» ولا تخمين |
| 7 | **تسليم نظيف لـ VE** | حمولة حقائق + نوع الفهرس — بلا قرار اعتماد في الواجهة |
| 8 | **تتبع إنساني** | حالات الشحن **حرفيًا** من رحلة القرار / لغة المنتج — لا اختراع حالات · لا رموز WF خامًا للمستخدم |
| 9 | **لا تخمين في بيانات الشجرة** | قاعدة رسمية — §2.1 |

### 2.1 قاعدة رسمية — لا تخمين

> **لا تخمين في بيانات الشجرة. إذا كان هناك أكثر من احتمال، يتوقف المسار ويطلب تحديدًا واضحًا.**

| صحيح | خطأ |
|------|-----|
| المستخدم يعطي الحد الأدنى لتحديد النية | نموذج قصير = النظام يخمن باقي الربط/الشخص |
| النظام يتحقق ويعرض ما فهمه قبل الإرسال | الاسم + الجنس + البحث وحدها كافية عند التصادم |
| عند غموض (تصادم أسماء، أكثر من أب محتمل، طرف زواج ملتبس) → توقف + سؤال بشري | اختيار صامت لأول نتيجة بحث |

**معنى «نماذج قصيرة» مع هذه القاعدة:** قصر النموذج = أقل حقول لازمة **للهوية والسياق**، لا إسقاط خطوات التأكيد. التأكيد البشري قبل الإرسال **جزء من المسار**، ليس «حقلًا إضافيًا اختياريًا».

### 2.2 Single Write — المعنى العملي في RX

| فرض | تفاصيل |
|-----|--------|
| **لا يوجد زر «حفظ في الشجرة» داخل RX** | المستخدم **يرسل طلبًا للمراجعة** فقط |
| لا كتابة مباشرة | ممنوع insert/update على `tree_*` / أحداث معتمدة / memory / cards من واجهة الزائر |
| الكتابة الوحيدة لاحقًا | عبر مسار WF عند `approved → applied` وخدمات الفهرس — خارج RX |
| شعور المستخدم | «ابدأ الآن» و«أرسل الطلب للمراجعة» **لا يغيّران الشجرة** |

## 3) نطاق النوايا — RX v1

### 3.1 معتمدة (من الفهرس فقط)

| نية العرض (الزائر) | النوع الداخلي | ملاحظات UX |
|--------------------|---------------|------------|
| أضف فردًا للعائلة | `tree_card` | حقائق الشخص + سياق الأب/الربط (بحث بشري) + **تأكيد هوية/مسار (§4.2.1)** + مراجعة نهائية قبل الإرسال |
| صحح بيانات شخص | `tree_edit` | اختيار شخص موجود ثم الحقول المراد تصحيحها فقط + مراجعة قبل الإرسال |
| أعلن وفاة | `event_death` | شخص + تاريخ (+ سبب إن لزم السياسة) + مراجعة نهائية |
| أعلن زواج | `event_marriage` | الطرفان + تاريخ + مراجعة نهائية |
| شارك ذكرى | `memory_card` | نص/وسائط + روابط أشخاص اختيارية + ملخص قبل الإرسال |
| اطلب بطاقة | `special_card` | نوع البطاقة + المستهدف + حقول النوع + ملخص قبل الإرسال |

**نية تشغيلية (ليست كروم الرئيسية للزائر):**

| نية | أين | النوع |
|-----|-----|--------|
| طلب إعادة تعيين الرقم السري | شاشة إدارة مخصّصة | `delegate_secret_reset` |

### 3.2 خارج النطاق (⬛ مؤجّل — **ليس ملغى**)

لا بطاقة نية · لا مسار · لا نسخة تجريبية في RX v1:

- أضف زوجة  
- أضف أبناء (كنية مستقلة)  
- أعلن ميلاد / مولود  
- «أعلن مناسبة» كآلة حالات جديدة  

| قاعدة | المعنى |
|--------|--------|
| **مؤجّل ≠ ملغى** | الباب يبقى مفتوحًا؛ رحلة مستقبلية يجب أن تبقى ممكنة |
| **لا إغلاق الباب في تصميم RX** | لا نفترض أن «أضف فردًا» أو «أعلن زواج» يغنيان نهائيًا عن زوجة/أبناء/ميلاد |
| **زوجة خصوصًا** | إعادة تصميم لاحقة مطلوبة لسلامة العلاقات — لا تُحسم هنا ولا تُقفل بنموذج RX v1 |
| عند حسم المنتج لاحقًا | صف فهرس → لغة المنتج → تحديث هذه المواصفة — ثم فقط |

## 4) هيكل التجربة (شاشات منطقية)

> شاشات منطقية — ليست أسماء ملفات ولا فرض إطار عمل.

### 4.1 الرئيسية — اختيار النية

```
┌──────────────────────────────────────────┐
│  ماذا تريد أن تفعل؟                      │
│                                          │
│  [ أضف فردًا للعائلة ]                   │
│  [ صحح بيانات شخص ]                      │
│  [ أعلن وفاة ]                           │
│  [ أعلن زواج ]                           │
│  [ شارك ذكرى ]                           │
│  [ اطلب بطاقة ]                          │
│                                          │
│  ── طلباتي ──                            │
│  (قائمة قصيرة لآخر العمليات + الحالة)    │
└──────────────────────────────────────────┘
```

| قاعدة | تفاصيل |
|--------|---------|
| عنوان الصفحة | **ماذا تريد أن تفعل؟** |
| بطاقات النية | نص العرض من الفهرس / لغة المنتج فقط |
| CTA الدخول للمسار | **ابدأ الآن** = الدخول إلى تدفق النية فقط — **لا يُرسل** ولا يغيّر الشجرة |
| لا تبويبات تقنية | لا «شجرة / مناسبات / بطاقات» كتصنيف DB |
| مدخل التتبع | قسم «طلباتي» أو رابط مكافئ — حالات بشرية |

### 4.2 نموذج النية — حقائق قصيرة + تأكيد

تدفق موحّد لكل نية A–F:

```
اختيار النية
    → [ ابدأ الآن ]          ← دخول المسار فقط
    → حقائق (١–٣ خطوات)
    → تأكيد هوية/سياق عند الحاجة (إجباري عند اختيار شخص/سياق — خاصة «أضف فردًا»)
    → مراجعة نهائية بشرية
    → [ أرسل الطلب للمراجعة ]  ← الإرسال الوحيد إلى VE/WF
```

| قاعدة | تفاصيل |
|--------|---------|
| **فصل لغة الأزرار** | **«ابدأ الآن»** = دخول التدفق فقط · **«أرسل الطلب للمراجعة»** = الخطوة النهائية فقط |
| ممنوع شعور مضلّل | المستخدم **لا** يشعر أن «ابدأ الآن» يغيّر الشجرة أو يُكمل الطلب |
| الخطوات | تجنّب معالج 5+ خطوات؛ إن لزم تقسيم، كل خطوة سؤال بشري واحد — التأكيد والمراجعة **ليستا** حشوًا يُحذف للسرعة |
| اختيار الشخص | بحث بالاسم + سياق عائلي؛ التخزين الداخلي `person_id` — المستخدم لا يكتب id |
| تواريخ | عبر DateEngine (عرض هجري/ميلادي متزامن) — بلا `new Date` أعمال |
| عند أكثر من احتمال | **توقف المسار** (§2.1) — لا اختيار صامت |

#### 4.2.1 P0 — تأكيد الهوية/السياق بعد اختيار شخص («أضف فردًا» وغيرها)

> **UX تأكيد بشري — ليس فحص VE.** حتى لو نجح البحث، يجب أن يرى المستخدم أين سيُربط الشخص ويؤكّد أن هذا المقصود.

##### فصل دلالي إلزامي (تعديل معتمد 2026-08-09 — Truth Before Speed)

هناك تأكيدان مختلفان — **لا يُخلطان**:

| النوع | المعنى | نتيجة «نعم» |
|--------|--------|-------------|
| **تصادم هوية الشخص المراد إضافته** | البحث وجد شخصًا موجودًا بنفس الاسم · «هل تقصد هذا الشخص الموجود؟» | **لا يُنشأ** طلب `tree_card` / إضافة — عرض «هذا الشخص موجود مسبقًا في الشجرة» + خيارات: عرض · تصحيح بيانات (`tree_edit`) · تغيير الاسم/السياق · أو «شخص آخر بنفس الاسم» بسياق أب صريح |
| **تأكيد الأب/السياق** | «سيُضاف الشخص **الجديد** تحت فلان» · «هل هذا هو الأب/السياق المقصود؟» | متابعة للمراجعة ثم الإرسال — فقط لفرد **جديد** لم يُؤكَّد أنه موجود كهوية |

**قاعدة ذهبية:** إذا أكد المستخدم أن الشخص الموجود هو المقصود، **فلا يجوز إنشاء طلب «إضافة شخص»**. إنشاء نسخة ثانية بعد تأكيد الوجود = تناقض منطقي.

**اكتمال أبناء الأب (تعديل 2026-08-09ب):** بعد اختيار الأب تُجلب **كل** صفوف `tree_children` بـ `parent_person_id` (بدون localStorage cache لهذا الحقل وبدون LIMIT يعرض جزءًا فقط). التصفية النصية تُطبَّق على المجموعة الكاملة في العميل. مثال تحقق: خميس → حسن، حسين، عبدالعزيز، منصور، مزيد.

**سلامة الكتابة (2026-08-09ج):** إن بقي ابن غائب عن `WHERE parent = مسار الأب` فالمشكلة غالبًا **عمود parent=NULL** (انجراف ثنائي الأعمدة) وليس LIMIT وحده — راقب مركز صحة البيانات → 🔴 سلامة البيانات؛ أصلح عبر preset الصيانة بعد موافقة. الكتابة الجديدة عبر Tree Engine ترفض `parent=NULL` (دين المواءمة ما زال على مسارات مندوب/إدارة مباشرة).

```
أضف فردًا → اسم (مثل حسن) → وُجد موجود
  → إن «نعم هذا هو المقصود» → ❌ لا طلب إضافة · رسالة وجود + تصحيح/تغيير
  → إن «شخص آخر بنفس الاسم» → تأكيد أب/سياق مختلف · لا تكرار صامت تحت نفس الأب
```

بعد اختيار **أب/سياق** من نتائج البحث — **خاصة عند تصادم الأسماء** — شاشة تأكيد واضحة:

```
┌──────────────────────────────────────────┐
│  تأكيد الأب / السياق                     │
│                                          │
│  سيُضاف الشخص الجديد «…» تحت:            │
│  [المسار الكامل للفرع / الأسلاف]         │
│                                          │
│  الفرع: …                                │
│                                          │
│  هل هذا هو الأب / السياق المقصود؟        │
│                                          │
│  [ نعم، هذا هو السياق ]                  │
│  [ اختيار سياق آخر ]                     │
└──────────────────────────────────────────┘
```

| قاعدة | تفاصيل |
|--------|---------|
| **إلزامي** | بعد كل اختيار من البحث يربط فردًا أو سياق أب/عائلة لنوايا تغيّر الشجرة |
| غير كافٍ وحده | الاسم · الجنس · نتيجة البحث — **بدون** المسار الكامل + تأكيد صريح |
| عند الرفض | «اختيار سياق آخر» يعود للبحث — لا متابعة صامتة |
| ينطبق أيضًا | اختيار شخص لوفاة / طرف زواج / تصحيح — بنفس روح «هل هذا المقصود؟» + سياق كافٍ |
| **بوابة هوية (RX soft gate)** | قبل إرسال «أضف فردًا»: إن وُجد تطابق اسم وأكّد المستخدم الوجود → حظر الإرسال (ليس بديلًا عن VE الكامل) |

#### حقائق دنيا مقترحة (تصميم — قابلة للضبط قبل الكود)

| النية | حقول الزائر (حد أدنى) | يبنيه النظام / لاحقًا |
|--------|------------------------|------------------------|
| أضف فردًا | الاسم · الجنس · أقرب سياق أب/عائلة (بحث + **تأكيد مسار**) · تاريخ ميلاد إن وُجد | فرع · ربط · فحوصات VE |
| صحح بيانات | الشخص (بحث + تأكيد) · الحقول المتغيّرة فقط | مقارنة «الآن vs مقترح» للمندوب |
| أعلن وفاة | الشخص (بحث + تأكيد) · تاريخ الوفاة | اتساق عائلي في VE |
| أعلن زواج | الطرف الأول · الطرف الثاني (كلٌ مع تأكيد) · التاريخ | تعارض زوجية في VE |
| شارك ذكرى | النص · وسائط اختيارية · أشخاص مرتبطون اختياريًا | حدود وسائط في VE |
| اطلب بطاقة | نوع البطاقة · المستهدف · حقول النوع | قواعد التكرار في VE/الخدمة |

### 4.3 المراجعة النهائية قبل الإرسال (تأكيد بشري إلزامي)

> أي طلب **يغيّر الشجرة** يحتاج صفحة تأكيد بشرية واضحة **قبل** «أرسل الطلب للمراجعة».

#### أضف فردًا

```
┌──────────────────────────────────────────┐
│  راجع قبل الإرسال                        │
│                                          │
│  الاسم: …                                │
│  الجنس: …                                │
│  الأب / السياق: …                        │
│  المسار: …                               │
│  تاريخ الميلاد: … (إن وُجد)              │
│                                          │
│  سيتم إرسال هذه المعلومات للمراجعة       │
│  (لن تُحفظ في الشجرة الآن)               │
│                                          │
│  [ أرسل الطلب للمراجعة ]                 │
│  [ تعديل ]                               │
└──────────────────────────────────────────┘
```

#### أعلن وفاة

| يعرض | |
|------|--|
| الشخص (باسم + سياق كافٍ) | تاريخ الوفاة |
| جملة: سيتم إرسال هذه المعلومات للمراجعة | ثم **أرسل الطلب للمراجعة** |

#### أعلن زواج

| يعرض | |
|------|--|
| الطرف الأول | الطرف الثاني | التاريخ |
| جملة: سيتم إرسال هذه المعلومات للمراجعة | ثم **أرسل الطلب للمراجعة** |

#### نوايا أخرى (تصحيح / ذكرى / بطاقة)

ملخص بشري مكافئ (النية · الحقول المتغيرة أو المحتوى · المستهدف) + نفس جملة المراجعة + **أرسل الطلب للمراجعة**.

| قاعدة | تفاصيل |
|--------|---------|
| لا إرسال من منتصف النموذج | الزر النهائي الوحيد للإرسال = **أرسل الطلب للمراجعة** |
| لا لغة «حفظ / إنشاء في الشجرة» | انظر §2.2 |
| Truth Before Speed | إن ظهرت نتيجة VE سلبية قبل/عند الإرسال — تصحيح أولًا |

### 4.4 بعد الإرسال — تأكيد + تتبع

```
┌──────────────────────────────────────────┐
│  تم الإرسال                              │
│  إضافة فرد · … · تم الإرسال              │
│                                          │
│  ● تم الإرسال                            │
│  ○ وصل للمندوب                           │
│  ○ تحت المراجعة                          │
│  ○ …                                     │
│                                          │
│  [ متابعة طلباتي ]   [ ابدأ شيئًا آخر ]  │
└──────────────────────────────────────────┘
```

### 4.5 حالات التتبع — حرفيًا من رحلة القرار (لا اختراع)

**المصدر الوحيد للعرض:** جدول لغة الحالة في [`REQUEST-DECISION-JOURNEY-v1.md`](./REQUEST-DECISION-JOURNEY-v1.md) §1.4 (ولغة المنتج).  
RX **لا تخترع** تسمية ولا تعيد تفسير الرموز.

| رمز WF | عرض الزائر | المعنى التشغيلي (للتوضيح في المواصفة فقط — لا يُعرض كرمز) |
|--------|------------|-------------------------------------------------------------|
| `submitted` | تم الإرسال | الطلب قُدِّم — **لم يُعيَّن بعد** لمندوب |
| `assigned` | وصل للمندوب | **تعيين** الطلب لمندوب (`assigned`) — **ليس** اعتمادًا إداريًا لمحتوى الطلب |
| `in_review` | تحت المراجعة | المندوب يعمل على الطلب |
| `needs_changes` | نحتاج معلومة إضافية منك | بانتظار تعديل من المقدّم |
| `approved` | تم قبول طلبك | قرار قبول المحتوى — **قبل** التطبيق على الشجرة |
| `applied` | تمت إضافة البيانات | طُبّق عبر الخدمة |
| `done` | اكتمل | اكتمل المسار |
| `rejected` | لم يُقبل (+ سبب مفهوم) | مرفوض |

#### توضيح حاسم — «وصل للمندوب»

| سؤال | جواب (من رحلة القرار — لا اختراع) |
|------|-------------------------------------|
| هل «وصل للمندوب» = اعتماد الإدارة لمحتوى الطلب؟ | **لا** — الاعتماد = `approved` → «تم قبول طلبك» |
| متى يظهر «وصل للمندوب»؟ | فقط عند حالة WF **`assigned`** (مُعيَّن للمندوب) |
| هل يظهر والزائر ما زال ينتظر قرارًا إداريًا مبكرًا والطلب `submitted`؟ | **لا** — يبقى «تم الإرسال» حتى يحدث التعيين فعليًا |
| ماذا يرى المندوب عند `assigned`؟ | «في طابورك — لم تبدأ بعد» (رحلة القرار) — لم يبدأ المراجعة بعد |

**ممنوع في التتبع:** `tree_card` · `REQ-…` كعنوان وحيد · JSON · أسماء أعمدة · حالات مخترعة خارج الجدول أعلاه.

### 4.6 نحتاج معلومة إضافية

عند `needs_changes` (من VE أو من المندوب عبر WF):

1. رسالة السبب بلغة بشرية (حقل/حقيقة ناقصة أو غموض يجب حسمه).  
2. نموذج قصير للحقول المطلوبة فقط.  
3. **تعديل** ثم **أرسل الطلب للمراجعة** (إعادة إرسال).  
4. العودة لمسار التتبع — نفس الطلب (لا إنشاء مكرر صامت).

### 4.7 فشل التحقق قبل الدخول للطابور

إن رفض VE الإرسال/التعيين:

| نتيجة VE | سلوك RX |
|----------|---------|
| يحتاج معلومة | نفس §4.6 — لا يُعرض كـ«مرفوض نهائي» إن كان قابلًا للتصحيح |
| مرفوض تحقق | سبب واضح · لا إرسال متكرر بنفس الحمولة الفاسدة دون تغيير |
| يمر | تسليم لـ WF · حالة «تم الإرسال» ثم التالية **حسب المحرك فقط** |

RX **تعرض** نتيجة VE — **لا تعيد تنفيذ** قواعد الهوية/التكرار/التعارض داخل الصفحة.

**استثناء بوابة UX (P0 · 2026-08-09):** إن أكد المستخدم صراحةً أن المطابق الموجود هو المقصود، RX **تحظر** إنشاء طلب إضافة قبل الوصول لـ VE — هذا فصل دلالي للواجهة وليس بديلًا عن محرك التحقق الكامل.

## 5) تسليم Validation Engine (عقد تصميم + وضوح الدور)

### 5.1 VE ليس مجرد «حقول ناقصة»

| RX تفعل | VE يمنع / يتحقق (أمثلة — القواعد تعيش في VE) |
|---------|-----------------------------------------------|
| تجمع الحد الأدنى من الحقائق | شخص موجود مسبقًا (تكرار) — **RX لديها بوابة soft عند تأكيد الوجود**؛ القرار النهائي الكامل يبقى في VE |
| تتحقق شكلًا بسيطًا (حقل فارغ ظاهر) | غموض تشابه أسماء دون تحديد |
| تعرض تأكيد الهوية/المسار للمستخدم | ربط بفرع خاطئ |
| **تحظر إرسال إضافة** إن أكّد المستخدم أن المطابق الموجود هو المقصود | — |
| تعرض أخطاء VE بلغة بشرية | تعارض زواج |
| تعيد الإرسال بعد التصحيح | شخص وفاة خاطئ / غير متسق |
| | طلب مكرر |
| | تعارض مع البيانات الحالية |

**Truth Before Speed:** أي فشل من الصف أعلاه = لا إرسال «رغم ذلك» ولا طفرة شجرة من RX.

### 5.2 عقد التسليم

```
RX ──► { intent_type, facts[], person_refs[], submitter_context }
          │
          ▼
        VE
          │
          ├── pass      → WF ينشئ/يحدّث الحالة
          ├── needs_info → RX تعرض الحقول/التحديد المطلوب
          └── reject    → RX تعرض السبب (بلا طفرة شجرة)
```

| RX تفعل | RX لا تفعل |
|---------|------------|
| تجمع الحقائق وتتحقق شكلًا بسيطًا (حقل فارغ) | تقرّر تكرار أشخاص أو صحة نسب أو تعارض زواج |
| تؤكّد فهم المستخدم لما سيُرسل (§4.2.1 · §4.3) | تخمّن عند تعدد الاحتمالات |
| تعرض أخطاء VE للمستخدم | تكتب على الشجرة عند «نجاح محلي» |
| تعيد الإرسال بعد التصحيح | تتخطّى VE «للسرعة» |

القواعد التفصيلية تُوثَّق وتُنفَّذ في [`VALIDATION-ENGINE.md`](./VALIDATION-ENGINE.md) — RX تصرّح بالدور والعقد فقط.

## 6) علاقة Workflow (استهلاك فقط)

| ما تستهلكه RX من WF | ما لا تبنيه RX |
|---------------------|----------------|
| الحالة الحالية بلغة المنتج **حرفيًا** من رحلة القرار | آلة حالات خاصة بالواجهة |
| إشعارات/تحديثات الحالة للعرض | تعيين المندوب يدويًا من الزائر |
| معرّف متابعة ثانوي إن لزم للدعم | مسار `status` قديم موازٍ كحقيقة |
| عرض «وصل للمندوب» فقط عند `assigned` | إعادة تفسير «وصل للمندوب» كاعتماد إداري |

أساس WF الحالي **provisional** — تصميم RX لا يفترض توسيع المحرك الآن؛ يفترض عقد العرض أعلاه.

### 7.3 أمثلة بطاقة تتبع

- ✅ «إضافة فرد · محمد … · تحت المراجعة»

## 8) As-Is → To-Be (الرئيسية فقط)

| As-Is | To-Be (RX v1) |
|-------|----------------|
| «إضافة بيانات للشجرة» / «إرسال البطاقة» | نية «أضف فردًا» + ابدأ الآن → … → أرسل الطلب للمراجعة |
| حقول جد١…٤ ظاهرة كأساس | سياق أب/عائلة مختصر + بحث + تأكيد مسار كامل |
| اختيار من بحث بلا تأكيد عند التصادم | شاشة هوية منفصلة إن وُجد الشخص · وشاشة «هل هذا هو الأب/السياق؟» للإضافة الجديدة |
| تأكيد «نعم المقصود» ثم طلب إضافة مكرّر | **محظور** — تأكيد الوجود = لا `tree_card` إضافة |
| مسارات مناسبة/ذكرى/بطاقة منفصلة اللغة | شبكة نوايا واحدة |
| تتبع ضعيف / حالات مخترعة | مسار شحن موحّد حرفيًا من رحلة القرار |
| تفكير بطاقة/DB / حفظ شجرة | تفكير فعل بشري · طلب للمراجعة فقط |

الصفحة الحالية للزائر = **legacy تجربة** إلى أن يُشحن RX بعد اعتماد هذه المواصفة — **لا تجميل تدريجي بلا مواصفة · لا تجميل legacy مندوب قبل اعتماد RX**.
