## 0) حالة الاعتماد · تجميد التنفيذ

| بند | القرار |
|-----|--------|
| **دور الوثيقة** | **مرجع معتمد (conception)** للفلسفة والتدفق واللغة — لا مواصفة تنفيذ جاهزة للشحن |
| **ما يعنيه الاعتماد** | يُخطَّط ويُراجع ويُنقَّح التصوّر هنا؛ **لا** يبدأ بناء الصفحة الجديدة ولا ربطها بالمحركات من هذه الوثيقة وحدها |
| **ما لا يعنيه** | ليس إذن بدء كود · ليس Enhancement للصفحة الحالية · ليس تجاوز سلّم RX → VE → Workflow |
| **تجميد التنفيذ** | **ممنوع** أي كود منتج (JS/CSS/HTML/SQL واجهة) لمساحة المندوب الجديدة حتى: اعتماد مراجعة الـ UX + بوابات السلّم أدناه |
| **الصفحة الحالية** | **legacy** — مجمّدة تجميليًا (§8) |

### 0.1 موقع هذه الوثيقة في السلّم (مهم)

```
Delegates v2 → Product Foundation → Request Experience
        → Validation Engine → Workflow Engine
        → Delegate Workspace  ← هذه المرحلة (تنفيذ لاحقًا بعد اعتماد UX)
        → Admin UX → …
```

| حقيقة | المعنى |
|--------|--------|
| **هذه الوثيقة الآن** | تصوّر UX كامل لمساحة المندوب — **تصميم مسبق للمرحلة** |
| **التنفيذ** | ⚪ مجمَّد — ينتظر: اعتماد مراجعة UX + Request Experience → Validation Engine → Workflow Engine |
| **الصفحة الحالية** | **legacy** — تُجمَّد تجميليًا؛ لا تُطوَّر تدريجيًا نحو هذا التصوّر |

> **قاعدة صارمة:** لن يبدأ أي كود حتى تُعتمد مراجعة الـ UX صراحةً وتُفتح بوابات السلّم. هذه الوثيقة تُجهّز القرار واللغة والتدفق فقط.

## 1) الغرض والتموضع المعماري

### 1.1 ماذا هي مساحة عمل المندوب؟

واجهة تنفيذ للمندوب تجيب عن سؤال واحد:

> **ماذا يجب أن أنجز الآن؟**

المندوب يدخل على **طلبات تحتاج مراجعتك**، يفتح طلبًا كـ**جلسة عمل مستقلة**، يستخدم الأدوات التي يحتاجها **داخل الجلسة فقط**، يُصدر قرارًا (قبول / طلب تعديل / رفض)، ثم ينتقل مباشرة إلى **الطلب التالي**.

### 1.2 ماذا ليست؟

| ليست | لأن |
|------|-----|
| لوحة إدارة شجرة | الشجرة أداة داعمة داخل الجلسة — ليست الصفحة الرئيسية |
| Admin console | لا مراقبة تدفق، لا bulk، لا SQL، لا Health Center |
| شاشة «اختر شخصًا ثم عدّل» | نقطة الدخول = **الطلب / النية** لا الشخص |
| تطوّر تدريجي لـ `alzidan-tree.html` + `delegate.js` | إعادة تصميم كاملة (Redesign) — الصفحة الحالية legacy |

### 1.3 الطبقة في المعمارية

```
المستخدم (مندوب)
        │
        ▼
 Delegate Workspace     ← هذه الطبقة (عرض + أفعال بشرية فقط)
        │ يستدعي
        ▼
 Workflow Engine        ← حالة الطلب · التعيين · الانتقال · Audit · إشعار
        │
        ▼
 Validation Engine      ← نتيجة التحقق · أسباب · تعارضات (يُعرض ولا يُعاد اختراعه)
        │
        ▼
 Family Engine / …      ← أثر البيانات بعد approved → applied فقط (Single Write Rule)
```

- الواجهة **بلا منطق أعمال** (حالات · تحقق · صلاحيات مصدرها المحركات).
- الصلاحيات من **Delegates v2**؛ الواجهة تعكسها ولا تكون مصدرها الوحيد.

## 2) العلاقة بلغة المنتج · تجربة الطلب · التحقق · السير

| المصدر | ماذا تستهلك مساحة المندوب منه؟ | ماذا لا تفعله؟ |
|--------|-------------------------------|----------------|
| **Product Language** | كل العناوين والأزرار والحالات بلغة المستخدم (عمود المندوب) | لا `tree_card` · لا `request_id` كعنوان · لا Parent/JSON |
| **Request Catalog** | نوع النية المعروضة (أضف فردًا · صحح بيانات · …) | لا نوايا خارج الفهرس |
| **Request Experience** | يقدّم الزائر النية والحقائق؛ المندوب يراها كجلسة | لا نماذج «بدء نية» للمندوب كمسار رئيسي |
| **Validation Engine** | يعرض نتيجة التحقق وأسباب التعارض/النقص **قبل** القرار | لا يعيد كتابة قواعد التحقق في JS الصفحة |
| **Workflow Engine** | يقرأ الطابور والحالة والمالك؛ يستدعي الانتقالات فقط | لا يخزّن حالة موازية · لا يكتب Audit يدويًا |
| **Family Engine** | أدوات قراءة/سياق (شخص · شجرة) داخل الجلسة عند الحاجة | لا كتابة شجرة مباشرة من UI (Single Write Rule) |

### 2.1 سلسلة المنتج (من الزائر إلى المندوب)

```
زائر: ماذا تريد أن تفعل؟     (Request Experience)
        ↓
Validation: هل الحقائق سليمة؟ (Validation Engine — يتحقق ولا ينفّذ)
        ↓
Workflow: تعيين · حالة · إشعار
        ↓
مندوب: ماذا يجب أن أنجز الآن؟ (Delegate Workspace — هذه الوثيقة)
        ↓
قرار → انتقال Workflow → تطبيق خدمة عند الاعتماد المتحقَّق
```

**Truth Before Speed:** المندوب يرى تحذيرات/تعارضات التحقق قبل القبول؛ السرعة لا تتجاوز جودة الشجرة.

## 3) هندسة المعلومات والتدفقات الأساسية

### 3.1 الهيكل (IA)

```
دخول المندوب (جلسة/هوية — خارج نطاق إعادة تصميم العمل)
        │
        ▼
┌─────────────────────────────┐
│  الرئيسية = صندوق الطلبات   │  ← الشاشة الافتراضية بعد الدخول
│  «طلبات تحتاج مراجعتك»      │
└──────────────┬──────────────┘
               │ فتح طلب
               ▼
┌─────────────────────────────┐
│  جلسة عمل الطلب             │  ← شاشة مستقلة لكل طلب
│  ملخص النية · الحقائق ·     │
│  نتيجة التحقق · أدوات سياقية│
│  قرارات: قبول / تعديل / رفض │
└──────────────┬──────────────┘
               │ بعد القرار
               ▼
        الطلب التالي في الطابور
        (أو فراغ إن انتهى الطابور)
```

**موديولات داعمة (ليست المنزل):**

| موديول | الدور في v1 |
|--------|-------------|
| الطلبات | **المنزل الوحيد بعد الدخول** / الطابور |
| جلسة الطلب | العمل الفعلي |
| الشجرة (أداة) | تُفتح **من داخل الجلسة فقط** عند الحاجة — **ممنوع** تبويب يومي منافس للطابور |
| المناسبات / الذكريات | أدوات سياقية حسب نوع الطلب من الفهرس — **داخل الجلسة فقط** |
| الحساب | خروج · فرع · حالة الحساب — مدخل ثانوي واحد في الرأس، لا قسم عمل |

> في هذا التصوّر: **الرئيسية ≡ صندوق الطلبات**. لا شريط تبويب (شجرة · مناسبات · ذكريات) بجانب الطابور. أي إشارة قديمة في الخارطة لموديولات متوازية تُقرأ عبر هذه القاعدة — لا «لوحة إدارة فرع».

### 3.2 التدفق الأساسي (Happy path)

1. المندوب يرى قائمة مرتّبة: **الأقدم أولًا** أو حسب أولوية المحرك — **هذه أول شاشة بعد الدخول**.  
2. يفتح أول/أي طلب بنقرة واحدة → Workflow: `assigned → in_review` (إن لزم).  
3. يراجع في **صفحة واحدة**: النية · من أرسل · الحقائق · نتيجة Validation · مقارنة عند التعديل.  
4. يفتح أدوات السياق **فقط عند الحاجة** (شخص · شجرة · وسائط) — ليست خطوة إلزامية.  
5. يقرّر من شريط أسفل ثابت: **قبول** أو **نحتاج معلومة إضافية** أو **لم يُقبل**.  
6. المحرك ينفّذ الانتقال + Audit + إشعار.  
7. تأكيد قصير جدًا → **انتقال تلقائي إلى الطلب التالي** (الزر «الطلب التالي» احتياطي إن تعذّر التلقائي).

**مسار الحد الأدنى (طلب نظيف قابل للقبول):** طابور → فتح → قبول → التالي.  
لا خطوات وسطى إلزامية (لا اختيار شخص · لا فتح شجرة · لا لوحة إحصاء) قبل القرار.

### 3.3 مبدأ الجلسة

- كل طلب = **جلسة عمل مستقلة** (سياق · أدوات · قرار).  
- لا «مساحة عمل عامة» تخلط عدة طلبات مفتوحة في لوحة واحدة معقّدة.  
- العودة للطابور متاحة دائمًا؛ الافتراضي بعد الإنجاز = **التالي تلقائيًا** — **ممنوع** الهبوط على الشجرة أو لوحة إدارة بين الطلبات.

## 4) الشاشات والحالات

### 4.1 شاشة الطابور (Inbox)

| عنصر | محتوى |
|------|--------|
| العنوان | طلبات تحتاج مراجعتك |
| السؤال الضمني | ماذا يجب أن أنجز الآن؟ |
| بطاقة طلب | نية بشرية + اسم/موضوع + من أرسل + حالة مفهومة + وقت الانتظار |
| ترتيب | من المحرك؛ الافتراضي الأقدم أولًا |
| تفاعل | نقرة واحدة → جلسة الطلب |

**حالات الطابور:**

| الحالة | العرض |
|--------|--------|
| تحميل | هيكل خفيف / هيكل عظمي — بلا جداول إدارية |
| قائمة غير فارغة | بطاقات عمودية (mobile-first) |
| فارغ | «لا طلبات بانتظارك الآن» + جملة طمأنة قصيرة — **بلا** توجيه لإدارة الشجرة |
| خطأ قراءة | رسالة عربية من المحرك — بلا أخطاء Supabase خام |

**ما لا يظهر في الطابور:** أعمدة تقنية · فلاتر bulk · إحصائيات كثيفة · شجرة · محرّر أشخاص.

### 4.2 شاشة جلسة الطلب (Work Session)

هيكل عمودي بسيط:

1. **رأس الجلسة:** النية (مثال: أضف فردًا للعائلة) · الحالة بلغة المستخدم · رجوع للطابور.  
2. **من أرسل / متى** — سطر واحد.  
3. **الحقائق المقدَّمة** — ما أدخله الزائر بلغة بشرية.  
4. **نتيجة التحقق** (من Validation Engine) — قبول للمسار / تحذيرات / نواقص / تعارضات بأسباب واضحة.  
5. **مقارنة** (إن انطبق — خاصة `tree_edit`): الحالي vs المقترح.  
6. **أدوات السياق** (أزرار ثانوية تظهر حسب الحاجة فقط).  
7. **شريط القرار الثابت أسفل الشاشة (موبايل):** قبول · نحتاج معلومة · لم يُقبل.

### 4.3 مقارنة الحالي vs المقترح (Compare)

| متى | العرض |
|-----|--------|
| تصحيح بيانات / تعديل حقائق | عمودان أو قائمتان: **المسجّل الآن** · **المقترح في الطلب** |
| إضافة فرد جديد | لا مقارنة حقول قديمة؛ عرض الحقائق + موقع مقترح في العائلة إن وُجد من التحقق |
| مناسبة / ذكرى / بطاقة | ملخص المحتوى المقترح؛ مقارنة فقط إن وُجدت نسخة سابقة ذات صلة |

قواعد العرض: أسماء حقول بشرية («تاريخ الميلاد» لا `birth_date_g`). التمييز البصري للتغيير فقط — بلا JSON.

### 4.4 نتائج القرار (Outcomes)

| قرار المندوب (واجهة) | انتقال Workflow النموذجي | ما يُطلب من المندوب |
|----------------------|---------------------------|---------------------|
| **قبول** | `in_review → approved` ثم المحرك → `applied` → `done` | تأكيد قصير؛ إن وُجدت تحذيرات Validation غير حاجزة تُعرض قبل التأكيد |
| **نحتاج معلومة إضافية** | `in_review → needs_changes` | **سبب مقروء إلزامي** (يصل للزائر بلغة المنتج) |
| **لم يُقبل** | `in_review → rejected` | **سبب مقروء إلزامي** |

بعد نجاح الانتقال:

1. رسالة قصيرة («تم قبول الطلب» / «أُرسل طلب التعديل» / «لم يُقبل الطلب») — ثوانٍ فقط، بلا شاشة وسيطة معقّدة.  
2. **الافتراضي:** انتقال تلقائي إلى **الطلب التالي** في الطابور. زر «الطلب التالي» ظاهر كاحتياطي/تأكيد سريع فقط.  
3. إن لم يبقَ طلب: شاشة الفراغ (§4.1) — بلا توجيه لإدارة الشجرة.  
4. **إيقاع الطابور:** المندوب يشعر أنه يُغلق مهامًا متتالية — ليس أنه يعود لـ«لوحة تحكم» بين كل قرار.

**ADR-006:** زر القبول لا يعني «نجاحًا نهائيًا» في الواجهة إلا بعد مسار التطبيق المتحقَّق الذي يوفّره المحرك؛ الواجهة لا تكتب الشجرة بنفسها.

### 4.5 حالات الجلسة الإضافية

| الحالة | السلوك |
|--------|--------|
| الطلب لم يعد ملك المندوب | رسالة + عودة للطابور |
| انتقال مرفوض بالصلاحية | رسالة Delegates عربية — بلا إعادة محاولة صامتة |
| Validation حاجز قبل القبول | تعطيل القبول أو مسار «لا يمكن القبول حتى تُصحَّح الحقائق» مع الأسباب |
| انقطاع شبكة | حفظ محلي غير مطلوب في v1؛ إعادة محاولة واضحة |

## 5) مبادئ التخطيط Mobile-first — وما لا يُعرض

### 5.1 يجب

- عمود واحد · إبهامي · قرارات في أسفل الشاشة.  
- بطاقات طلب قصيرة قابلة للمسح البصري في ثوانٍ.  
- جلسة طلب = صفحة كاملة (أو طبقة كاملة) لا لوحة متعددة الأعمدة.  
- نصوص عربية RTL · أفعال قصيرة.  
- سرعة الإدراك: النية أولًا، التفاصيل التقنية أبدًا في الواجهة الأولى.

### 5.2 ممنوع أن تشعر كـ Admin console

لا تُعرض افتراضيًا:

| ممنوع في مساحة المندوب | بديل |
|------------------------|------|
| جداول عريضة متعددة الأعمدة | بطاقات |
| شريط جانبي بموديولات كثيرة | طابور → جلسة |
| لوحة إحصائيات / اختناقات / حمل مندوبين | Admin UX لاحقًا |
| SQL · Health · Integrity · Bulk | خارج الطبقة |
| الشجرة كصفحة منزل | أداة داخل الجلسة |
| مصطلحات DB / Admin | لغة المنتج |
| حذف كإجراء افتراضي ظاهر | no default delete (الخارطة) |
| اختيار شخص كخطوة أولى للعمل اليومي | فتح طلب أولًا |

### 5.3 كثافة المعلومات

الشاشة الأولى بعد الدخول: **قائمة طلبات فقط** (+ هوية مختصرة في الرأس).  
كل ما عدا ذلك يُكشف عند الحاجة داخل الجلسة.

## 6) أمثلة لغة (Human labels)

المصدر الحاكم: [`PRODUCT-LANGUAGE.md`](./PRODUCT-LANGUAGE.md). أمثلة تشغيلية لمساحة المندوب:

### 6.1 عناوين وأزرار

| سياق | نص معتمد | تجنّب |
|------|----------|--------|
| المنزل | طلبات تحتاج مراجعتك | Queue · Inbox · Pending rows |
| السؤال | ماذا يجب أن أنجز الآن؟ | إدارة الشجرة · اختر الأب |
| فتح | مراجعة الطلب | Open record |
| قبول | قبول الطلب | Approve / Apply row |
| تعديل | نحتاج معلومة إضافية | needs_changes · Request changes (إنجليزي في UI) |
| رفض | لم يُقبل | Reject |
| التالي | الطلب التالي | Next ticket |
| مقارنة | المسجّل الآن · المقترح | Current payload · Diff JSON |
| أداة | عرض الشخص · عرض موقعه في العائلة | Open node · Parent path |

### 6.2 بطاقة في الطابور (مثال)

> **أضف فردًا للعائلة**  
> محمد بن حبيب — أرسله خالد  
> وصل للمندوب · منذ ساعتين  

### 6.3 رأس جلسة (مثال)

> **صحّح بيانات شخص**  
> تحت المراجعة  
> المقدَّم: سارة · فرع مزيد  

### 6.4 أسباب (للزائر عبر المحرك)

| نوع | مثال صياغة |
|-----|-------------|
| تعديل | نحتاج تاريخ الميلاد بالهجري أو الميلادي بوضوح. |
| رفض | لم نتمكن من مطابقة الشخص في العائلة بالمعلومات المتاحة. |

لا تُعرض رموز مثل `TREE-001` كعنوان للمندوب اليومي؛ إن لزم التشخيص فطبقة ثانوية لاحقة — ليس v1 الأساسي.

## 7) أدوات تظهر فقط داخل جلسة الطلب

الأدوات **مشروطة بنوع الطلب** من [`REQUEST-CATALOG.md`](./REQUEST-CATALOG.md) وبنتيجة التحقق — ليست شريط أدوات دائمًا.

| أداة | متى تظهر | ماذا تفعل (عرض) |
|------|----------|------------------|
| عرض الشخص | عند وجود شخص مرتبط / مرشّح | بطاقة حقائق للقراءة |
| عرض موقعه في العائلة | عند الحاجة لتأكيد النسب/الموقع | قراءة شجرة/سياق — ليست محرّر إدارة |
| مقارنة المسجّل vs المقترح | خاصة تصحيح البيانات | §4.3 |
| وسائط مرفقة | ذكرى / مناسبة / بطاقة فيها ملفات | معاينة |
| نتيجة التحقق التفصيلية | دائمًا إن وُجدت مخرجات Validation | أسباب واضحة |
| قبول / طلب معلومة / رفض | دائمًا في الجلسة النشطة للمالك | §4.4 |

**قواعد الأدوات:**

1. لا تظهر أداة شجرة كاملة كـ«إدارة فرع» داخل الجلسة.  
2. أي كتابة على البيانات العائلية تمر Workflow + Validation فقط.  
3. لا حذف افتراضي ظاهر.  
4. الصلاحية إن منعت الأداة: إخفاء أو تعطيل + رسالة عربية من Delegates — الفرض في المحرك.

---

## 8) الصفحة الحالية = Legacy — تجميد التحسين التجميلي

| البند | القرار |
|-------|--------|
| الصفحة الحالية (`pages/alzidan-tree.html` + `assets/js/delegate.js` + لوحات العائلة/المناسبات) | **legacy** — مبنية على **إدارة شجرة / اختيار شخص** |
| التحسين التجميلي عليها | **موقوف** — لا ألوان · لا إعادة ترتيب بطاقات · لا «تحسين UX» تدريجي نحو هذا التصوّر |
| الإصلاحات الحرجة فقط | أمان · كسر دخول · انحدار بيانات — خارج نطاق «تجميل» |
| الاستبدال | **إعادة تصميم كاملة** وفق هذه الوثيقة عند مرحلة Delegate Workspace على السلّم |
| لا Enhancement | ممنوع مسار «نحوّل الداشبورد الحالي لطابور» كحل وسط طويل الأمد |

نص الخارطة الحالي للمندوب («إدارة العائلة: اختر شخصًا…») **يناقض** السؤال المحوري الجديد — يُستبدل لا يُرقَّع.

## 9) جرد: ما يُحفظ محتملًا vs ما يُستبعد

اطّلاع تشغيلي على الوضع الحالي (ليس للتمديد):

### 9.1 مرشّح للإنقاذ لاحقًا (مفهوم / نمط — لا نسخ التصميم)

| عنصر | سبب الإنقاذ المحتمل |
|------|---------------------|
| تدفق دخول المندوب + رسائل الرفض العربية (معطّل / بلا صلاحية / سر غير مطابق) | نمط لغة وصلاحيات Delegates v2 — يُعاد توظيفه لا نسخه البصري |
| `confirmTypedText` / تأكيد كتابة لنص حسّاس | نمط أمان لقرارات حساسة إن لزم لاحقًا |
| معاينة وسائط المندوب (أنماط CSS خفيفة) | قد تُستلهم للمعاينة داخل الجلسة |
| وحدات قراءة الشخص / الهوية الكانونية (`canonical-person` وغيرها) | كـ**خدمات قراءة** تُستدعى من الجلسة — لا كواجهة منزل |
| جلسات المندوب / فرض الصلاحية في RPC | طبقة بيانات — تبقى؛ الواجهة الجديدة تستهلكها |

### 9.2 يُستبعد من المنزل والتجربة الأساسية

| عنصر | سبب الاستبعاد |
|------|----------------|
| الشجرة العامة + «إضافة أبناء» كنقطة دخول | tree-first |
| تلميح الداشبورد «اختر شخصًا…» | يناقض requests-first |
| `family-management-panel` كسطح العمل اليومي | محرّر شجرة إداري الشعور |
| بطاقات المناسبات/الذاكرة كأقسام منزل موازية للطابور | تُحوَّل لأدوات جلسة حسب النوع |
| كتابة مباشرة على `tree_children` من واجهة المندوب لمسار الفهرس | يخالف Single Write Rule عند اكتمال المحركات |
| مصطلحات/حقول تفكير قاعدة بيانات ظاهرة للمندوب | Product Language · No Database Thinking |
| تخطيط متعدد البطاقات/الأقسام كـ console | يخالف البساطة وmobile-first |

**الخلاصة:** لا يُعاد استخدام تصميم الصفحة الحالية كأساس. الإنقاذ = أنماط صلاحيات/دخول وخدمات قراءة — لا IA ولا هيكل الشاشات.

## 11) معايير قبول التصوّر قبل بدء التنفيذ

يُعتبر هذا التصوّر **جاهزًا للتحويل لكود** فقط عندما يتحقق **كل** ما يلي — بما فيها **اعتماد مراجعة UX** أدناه.

### 11.0 النقاط الثلاث الحرجة (اختبار فلسفة التجربة)

| # | السؤال | معيار النجاح في هذا التصوّر |
|---|--------|------------------------------|
| 1 | **أول شاشة يراها المندوب** — هل تعرض العمل المطلوب فورًا؟ | بعد الدخول: طابور «طلبات تحتاج مراجعتك» فقط (+ هوية مختصرة). بطاقة = نية + موضوع + مرسل + حالة + انتظار. نقرة → جلسة. **لا** شجرة · لا فلاتر bulk · لا إحصاء · لا تبويبات عمل منافسة. |
| 2 | **جلسة العمل داخل الطلب** — هل يُنهى الطلب بأقل عدد خطوات؟ | مسار نظيف: فتح → مراجعة صفحة واحدة → قرار من الشريط السفلي → تأكيد قصير عند اللزوم. الأدوات اختيارية. السبب إلزامي فقط لتعديل/رفض. **لا** اختيار شخص كخطوة أولى · **لا** قفز لشاشات إدارة. |
| 3 | **الانتقال للطلب التالي** — هل يشعر بطابور مهام لا لوحة إدارة؟ | بعد القرار: التالي **تلقائيًا** (زر احتياطي). الفراغ بلا توجيه للشجرة. ممنوع الهبوط على لوحة/شجرة بين المهام. |

إن ضعفت أي نقطة من الثلاث → يُراجع التصوّر هنا قبل أي شريحة كود. الصفحة الناتجة يجب أن تختلف جذريًا عن الحالية — لا نسخة محسّنة.

### 11.1 بوابات السلّم (إلزامية)

- [ ] مراجعة UX معتمدة صراحةً (هذه الوثيقة مرجع conception + النقاط الثلاث ✅)  
- [ ] Delegates v2 🟢 (قبول)  
- [ ] Product Foundation 🟢 (تجميد الدستور الحي)  
- [ ] Request Experience منفَّذ بما يكفي لتغذية الطلبات بلغة النية  
- [ ] Validation Engine يوفّر نتائج/أسباب قابلة للعرض للمندوب  
- [ ] Workflow Engine مغلق/مستقر على السلّم (حالات · تعيين · انتقال · Audit · إشعارات من الانتقال)

### 11.2 اتساق الدستور

- [ ] السؤال المحوري للمندوب = **ماذا يجب أن أنجز الآن؟**  
- [ ] **الطلبات أولًا · الأدوات ثانيًا · البساطة قبل كثرة الخيارات**  
- [ ] المنزل = طابور طلبات — ليس شجرة · بلا تبويبات عمل منافسة  
- [ ] الطلب = جلسة عمل مستقلة  
- [ ] الأدوات داخل الجلسة فقط  
- [ ] بعد الإنجاز → الطلب التالي تلقائيًا  
- [ ] لا منطق حالات/تحقق في الواجهة  
- [ ] Single Write Rule محترم في التصميم  
- [ ] لغة المنتج بلا مصطلحات محظورة  
- [ ] الصفحة الحالية معلّمة legacy ومجمّدة تجميليًا (هذه الوثيقة §8)

### 11.3 جاهزية التصميم للتنفيذ

- [ ] أنواع الفهرس الستة لها مسار جلسة موصوف (أدوات + مقارنة إن لزم)  
- [ ] مسارات القبول / التعديل / الرفض موصوفة مع إلزام السبب حيث يلزم  
- [ ] حالات الفراغ والتحميل والخطأ موصوفة  
- [ ] فصل واضح عن Admin UX  

عندها فقط تُفتح شريحة تنفيذ **Delegate Workspace v1** في الخارطة — على **مراحل** (§13) لا دفعة واحدة.

## 13) شرائح تنفيذ مقترحة (بعد الاعتماد فقط — ليست إذن بدء)

> تُنفَّذ **بعد** اعتماد مراجعة UX + بوابات السلّم. ترتيب مقترح — لا big bang:

| مرحلة | النطاق | نتيجة ملموسة |
|--------|--------|----------------|
| **A — Inbox** | شاشة الطابور فقط: قائمة · بطاقة · فراغ · خطأ · فتح جلسة | المندوب يرى «ماذا يجب أن أنجز الآن؟» فورًا |
| **B — Session** | جلسة الطلب: ملخص · حقائق · Validation · مقارنة · شريط قرار · أسباب | إنهاء طلب بأقل خطوات داخل سياق واحد |
| **C — Next-queue** | بعد القرار: تأكيد قصير → التالي تلقائيًا · فراغ الطابور | إيقاع طابور مهام لا لوحة إدارة |
| **D — Contextual tools** | أدوات الجلسة المشروطة بالنوع (شخص · موقع عائلي · وسائط) | أدوات ثانيًا — تظهر عند الحاجة فقط |
| **E — Engine hard-wiring** | ربط كامل Workflow/Validation/Delegates · إزالة أي مسار كتابة موازٍ | الواجهة بلا منطق أعمال |

الصفحة الحالية تبقى legacy حتى استبدال واضح بمسار A→E — لا Enhancement تدريجي نحو هذا التصوّر.

---

## 12) ملخص قرارات UX (للمراجعة السريعة)

1. **Requests-first** — لا person-first.  
2. **إعادة تصميم** — لا Enhancement للصفحة الحالية.  
3. **جلسة لكل طلب** — أدوات سياقية فقط.  
4. **قرار → التالي تلقائيًا** — إيقاع طابور مهام.  
5. **Mobile-first وبسيط** — ليس admin console · بلا تبويبات عمل منافسة.  
6. **لغة بشرية** من Product Language.  
7. **المحركات تقرر** — الواجهة تعرض وتنفّذ أفعالًا بشرية فقط.  
8. **مرجع معتمد (conception) · ليس للتنفيذ بعد** — كود فقط بعد اعتماد مراجعة UX + RX → VE → Workflow، وعلى مراحل (§13).

---

**هذه الوثيقة مرجع UX معتمد (conception) فقط — ليس للتنفيذ بعد.**  
أي طلب «حسّن صفحة المندوب الحالية» أو «ابدأ الكود الآن» يُرفض؛ المسار الصحيح = اعتماد مراجعة الـ UX ثم انتظار السلّم ثم بناء مساحة العمل على مراحل وفق ما ورد هنا.
