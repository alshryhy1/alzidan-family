# عائلة الزيدان — Engineering Roadmap (إدارة مشروع + مرجع هندسي)

**الحالة:** معتمد رسميًا — وثيقة إدارة مشروع (ليست قائمة مزايا فقط)  
**التاريخ:** 2026-08-07  
**آخر تحديث تخطيط:** 2026-08-08 — اعتماد المعمارية متعددة السنوات · Workflow Engine مستقل · مبادئ المنتج · ترتيب المراحل الكانوني · مواصفة سير الطلبات  
**القرارات المعمارية المقفلَة:** [`docs/ADR.md`](./ADR.md)  
**مواصفة سير الطلبات:** [`docs/WORKFLOW-SPECIFICATION-v1.md`](./WORKFLOW-SPECIFICATION-v1.md)

وثيقة التنفيذ الهندسية الرسمية لمشروع عائلة الزيدان. المنصة = **بيانات عائلية + سير اعتماد (approval workflow)** — ليست شجرة فقط. تُدار كـ**برنامج مشاريع** بثلاثة مسارات + طبقات معمارية ثابتة + بنية تحتية مشتركة.

**سياسة عامة للمشروع:** لا «مقبول / تم» بلا تطبيق متحقَّق — على الطلبات، الصور، الزوجات، الدمج، وأي اعتماد لاحق.

**الهدف التنفيذي الحالي:** إكمال **Delegates v2** (صلاحيات كاملة) → **Workflow Engine v1** → **Delegate Workspace v1** → **Admin UX**. UX الموبايل **بعد** مراحل الإدارة فقط. لا يُبدأ تنفيذ Delegate Workspace قبل اعتماد مواصفة السير.

## 1) المعمارية الأساسية (Core Architecture) — ثابتة

**غير قابلة للتغيير إلا بقرار معماري صريح (ADR).** الطبقات من الأعلى للأسفل:

```
Presentation
  ├── Admin Workspace      ← مراقبة التدفق والاختناقات
  ├── Delegate Workspace   ← إنجاز العمل على الطلب
  └── Visitor Portal       ← متابعة المقدّم/الزائر
        ↓
Workflow Engine            ← طبقة مستقلة بالكامل (ليست جزءًا من أي واجهة)
        ↓
Business Services
        ↓
Data Layer
```

### فصل المسؤوليات (لا تُخلط)

| الطبقة | المسؤولية | تعرف عن الواجهة؟ |
|--------|-----------|------------------|
| **Delegates v2** | من لديه صلاحية (دور · فرع · عمليات مسموحة · تفعيل) | لا — كتالوج وصلاحيات |
| **Workflow Engine** | ماذا يحدث للطلب (إنشاء · تعيين · انتقال حالة · إشعار · Audit · deep link) | **لا شيء** عن شكل الشاشة |
| **Delegate Workspace** | كيف يعمل المندوب (استلام · مراجعة · أدوات في سياق الطلب · قرار · التالي) | واجهة تنفيذ فقط |
| **Admin Workspace** | كيف يراقب المدير التدفق (أين عالق · الحمل · التأخير · الاختناقات) | واجهة مراقبة فقط |

- Workflow Engine **ليس** جزءًا من Delegate Workspace ولا Admin UI.
- كل أنواع الطلبات (`tree` / `event` / `memory` / `special_card` / مستقبلًا) تشترك في **نفس عُقد المحرك** — الفرق = **Request Type** فقط.
- المواصفة: [`WORKFLOW-SPECIFICATION-v1.md`](./WORKFLOW-SPECIFICATION-v1.md) · القرار: **ADR-010**.

## 1ب) مبادئ المنتج (Product Principles) — ثابتة

| # | المبدأ |
|---|--------|
| 1 | **الطلب محور النظام** |
| 2 | كل طلب له **مالك واحد واضح في كل لحظة** |
| 3 | كل انتقال حالة **يُسجَّل** (Audit) |
| 4 | **لا عملية خارج Workflow Engine** |
| 5 | الواجهات **بلا منطق أعمال** — تستخدم المحرك |

### قاعدة بوابة الميزة (Feature Gate) — قبل أي كود ميزة جديدة

1. صلاحية جديدة؟ → **Delegates v2**
2. تضيف/تغيّر حالة طلب؟ → **Workflow Engine**
3. عرض/تنفيذ فقط؟ → **Delegate Workspace** أو **Admin Workspace**

خرق البوابة = رفض التصميم قبل التنفيذ.

### مبادئ هندسية مكمّلة (ما زالت سارية)

| # | المبدأ |
|---|--------|

| E2 | **لا قبول بلا تطبيق متحقَّق** (ADR-006) |
| E3 | محرك الموبايل = منطق الويب في بناء العقد (ADR-005) |
| E4 | حماية البيانات قبل أي إصلاح (Backup → Scan → تقرير) |
| E5 | كل Patch: Validation + مسار Rollback |
| E6 | الترتيب الكانوني: **Delegates v2 → Workflow Engine v1 → Delegate Workspace v1 → Admin UX** ثم UX الموبايل |
| E7 | ممنوع القفز إلى UX الموبايل قبل إغلاق/موافقة مراحل الإدارة |
| E8 | **قواعد الانحدار (§8) غير قابلة للتفاوض** |
| E9 | مواصفة السير معتمدة قبل بدء تنفيذ Delegate Workspace |

## 2) Canonical Person Identity

```
person_id          ← هوية مستقلة مستقرة
    ↓
Node Path          ← موقع كانوني في الشجرة
    ↓
Display Name       ← للعرض
    ↓
Search Name        ← للبحث/التطبيع
```

كل كتابة تمر بـ `person_id`. ممنوع الربط الغامض بالاسم (`limit(1)` / `min()` على تطابق متعدد) **عند توفّر `person_id`**.

## 4) البرامج الثلاثة (فصل صارم)

العمل يُصنَّف تحت أحد البرامج التالية — لا تُخلط أولويات «إصلاح بيانات» مع «مزايا تطبيق» في نفس الشريحة التنفيذية.

### أ) برنامج إصلاح البيانات

| المسار | المحتوى | الحالة |
|--------|---------|--------|
| **Integrity** | محرك سلامة قراءة فقط (views + RPC تقرير) | 🟡 v2 بانتظار SQL · أساس v1/تقرير 🟢 |
| **Health Center** | واجهة المدير للمشاكل (قراءة فقط) | 🟢 |
| **Tree Repair** | تنظيف/إصلاح يدوي + dry-run؛ لا auto-repair من UI | 🟢 مغلق للتخطيط (يدوي) |
| **Data Migration** | Versioning · COPY-ME · backfill هويات/تواريخ | 🔵/🟡 حسب الملف المعلّق |

**بوابة:** أي إصلاح يكتب على الشجرة → Backup → Dry Run → موافقة → Apply → Audit. Health Center **لا** يطلق إصلاحًا تلقائيًا.

## 5) بنية تحتية — DateEngine (ADR-009)

**ليست ملاحظة جانبية.** DateEngine طبقة بنية تحتية مشتركة عبر البرامج الثلاثة.

| # | البند | الحالة |
|---|--------|--------|
| **DE-1** | مكتبة `assets/js/modules/date-engine.js` (parse / validate / convert / format / normalizeDigits / synced pair / timestamp guard) | 🟢 |
| **DE-2** | ADR-009 + حظر `new Date()` لتواريخ الأعمال | 🟢 موثّق |
| **DE-3** | مستهلك أول: حارس + تحقق حي على `polls-ends-at` | 🟢 |
| **DE-4** | ربط **كل** نماذج الميلاد/الوفاة/المناسبات بـ `toSyncedPair` | ⚪ دين تقني |
| **DE-5** | هجرة مخطط تدريجية لأعمدة `*_g` / `*_h` حيث ينقص الزوج | ⚪ — ليست في الجولة الحالية |

**قاعدة غير قابلة للتفاوض:** أي تاريخ أعمال جديد → DateEngine. أعمدة `timestamptz` ميلادية ترفض سنوات هجرية (`DATE-002`). انظر أيضًا § قواعد الانحدار.

## 6) Tree Engine v2 — مرحلة مستقلة

مرحلة منتج/معمارية **خاصة** (وليست بندًا فرعيًا تحت Admin UX). تُنفَّذ بعد استقرار الكتابة الحالية وIntegrity قراءة فقط، وقبل توسيع إصلاحات تلقائية واسعة.

| القدرة | الوصف | الحالة |
|--------|--------|--------|
| **person_id فقط** | كل نقل/ربط/دمج عبر UUID؛ لا مسار اسم عند وجود هوية | ⚪ (جزئيًا مفروض في مسارات الكتابة الحالية 🟢) |
| **لا name link** | إزالة بقايا حل الأب/الشخص بالاسم في محرك الشجرة | ⚪ دين تقني |
| **Duplicate detection** | اكتشاف أشخاص/عقد مكررة قبل الدمج | ⚪ |
| **Merge persons** | دمج هويتين مع سجل تدقيق + dry-run | ⚪ |
| **Move branches** | نقل فرع تحت أب جديد بـ `person_id` | ⚪ |
| **Dry Run** | كل عملية كتابة تعرض أثرًا متوقعًا قبل التنفيذ | ⚪ إلزامي عند البدء |
| **Rollback** | مسار استرجاع موثّق لكل عملية جماعية | ⚪ |

**علاقة بالبرامج:** تخدم برنامج (أ) إصلاح البيانات وتُغذي Admin عبر موديول الشجرة — دون خلطها مع مزايا تطبيق (ج).

## 8) قواعد الانحدار (Regression Rules) — غير قابلة للتفاوض

تُراجع في كل PR يمس الشجرة أو الاعتماد أو التواريخ أو الواجهة الإدارية:

| # | القاعدة |
|---|---------|
| **R-1** | **لا ربط بالاسم إذا توفّر `person_id`** — أي `limit(1)` / تطابق اسم متعدد مع تجاهل UUID = رفض |
| **R-2** | **لا حذف تدميري مباشر من الواجهة بلا ضمانات** — تأكيد صريح + (حيث ينطبق) dry-run / صلاحية / أثر معروض |
| **R-3** | **إصلاحات الشجرة تبدأ بـ Dry Run** — لا Apply صامت |
| **R-4** | **لا تُعرض أخطاء Supabase الخام للمستخدم النهائي** — رسالة عربية + رمز خطأ (`TREE-*` / `REQ-*` / …) |
| **R-5** | **كل تواريخ الأعمال عبر DateEngine** — لا `new Date(...)` لتواريخ المجال (ADR-009) |
| **R-6** | **تغييرات الشجرة → Audit** — كل اعتماد/إصلاح/دمج/نقل يكتب سجلًا قابلًا للمراجعة |
| **R-7** | **Health Center قراءة فقط** — ممنوع auto-repair من واجهة مركز الصحة |
| **R-8** | **لا منطق سير في الواجهة** — انتقالات الحالة والصلاحيات عبر Workflow Engine + Delegates فقط (ADR-010) |

خرق أي قاعدة أعلاه يوقف إغلاق البند حتى التصحيح أو ADR جديد صريح.

## 9) Architecture Decisions (ADR)

قرارات معمارية **مقفلة** — ليست اقتراحات. التفاصيل الكاملة في [`docs/ADR.md`](./ADR.md).

| ADR | القرار |
|-----|--------|
| ADR-001 | الهوية تعتمد على `person_id` (Canonical Person Identity) |
| ADR-002 | ممنوع الربط بالاسم عند الكتابة |
| ADR-003 | Event Bus هو المصدر الوحيد لأحداث المجال بعد الاعتماد |
| ADR-004 | Health Center مرجع صحة البيانات (Diagnostics للتفاصيل التقنية) |
| ADR-005 | محرك شجرة واحد — Web / Admin / Mobile بلا محركات متباعدة |
| ADR-006 | لا قبول بلا تطبيق متحقَّق (سياسة عامة) |
| ADR-007 | حماية Patch 0 قبل أي إصلاح يمس البيانات |
| ADR-008 | سياسة الكاش مربوطة بالأحداث وإصدارات البيانات |
| ADR-009 | DateEngine موحّد (هجري⇄ميلادي) — بنية تحتية؛ لا `new Date()` لتواريخ الأعمال؛ لا هجري في timestamp ميلادي |
| ADR-010 | **Workflow Engine طبقة مستقلة** — بلا UI؛ كل أنواع الطلبات نفس العُقد؛ الواجهات بلا منطق أعمال |

أي خرق لهذه القرارات يُوقف الإغلاق حتى يُصحَّح أو يُوثَّق ADR جديد صراحةً.

## 18) Data Integrity Engine

محرك **دائم** (برنامج أ): أبناء بلا أب، أب بلا فرع، `parent_person_id`، `person_id` مكرر، cycles، زوجة بلا زوج، أبناء خارج الفرع، `approved` بلا أثر، أخبار منتهية ظاهرة. يغذي Health Center.
