## ADR-001 — الهوية تعتمد على `person_id`

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

Canonical Person Identity هي العمود الفقري للشجرة. الطبقات بالترتيب:

```
person_id          ← هوية مستقرة (لا تتغير)
    ↓
Node Path          ← موقع كانوني في الشجرة
    ↓
Display Name       ← للعرض
    ↓
Search Name        ← للبحث/التطبيع
```

كل كتابة وربط واعتماد يمر عبر `person_id`.

### Consequences

- تُحل مشاكل تشابه الأسماء وتكرار العرض (صالح/صالح لاحم) عند الجذر.
- أي مسار كتابة جديد يجب أن يقبل/يُنتج `person_id` قبل التأثير على الشجرة.
- Display/Search Name ليسا هوية ولا يُستخدمان كمفتاح ربط عند الكتابة.

## ADR-002 — ممنوع الربط بالاسم عند الكتابة

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

يُمنع الربط الغامض بالاسم وقت الكتابة — بما في ذلك `limit(1)` أو `min()` أو أي اختيار عشوائي على تطابق اسم متعدد.

### Consequences

- عند غموض التطابق: فشل صريح برمز خطأ (`TREE-001` أو ما يعادله) بدل اختيار صامت.
- البحث بالاسم مسموح للعرض فقط؛ الكتابة تتطلب هوية محلولة.
- إصلاحات البيانات القديمة تمر عبر Migration موثّق وليس عبر «تخمين بالاسم».

## ADR-003 — Event Bus مصدر وحيد لأحداث المجال بعد الاعتماد

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

بعد أي اعتماد ناجح ومتحقَّق (ابن / زوجة / صورة / دمج / تعديل / أخبار)، يُصدر حدث مجال واحد موثّق عبر Event Bus. الشجرة والويب والموبايل والودجت والكاش والإشعارات تستهلك هذا المصدر فقط.

### Consequences

- لا تحديث صامت في مسار واحد مع ترك الباقي.
- سياسة الكاش مربوطة بالأحداث وإصدارات البيانات.
- أي مشترك جديد (منصة/ودجت) يُسجَّل كمستهلك للأحداث لا كمسار جانبي.

## ADR-004 — Health Center مرجع صحة البيانات

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

**Health Center** هو المرجع التشغيلي لصحة البيانات أمام المدير (المشاكل القابلة للإصلاح وعداداتها).  
**Diagnostics** للتفاصيل التقنية (Sync، Migration، Build، Widget Refresh، Backup، Scan، الإصدارات).

### Consequences

- لا يُعتبر النظام «سليمًا» بوجود مشاكل غير مفسَّرة في Health Center.
- Integrity Engine يغذّي Health Center بشكل دائم، وليس تقرير Patch 0 فقط.
- Diagnostics لا يستبدل Health Center ولا يُعرض كبديل للمدير.

## ADR-005 — محرك شجرة واحد (Single Tree Engine)

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

منطق بناء العقد وقواعد الشجرة واحد مشترك بين Web وAdmin وMobile. يُمنع وجود محركات متباعدة أو قواعد عرض تُعيد تفسير الهوية بشكل مختلف لكل منصة.

### Consequences

- إصلاح التكرار في الموبايل (مثل البند 36) يكون في طبقة العرض/البناء المشتركة أو المتوافقة — لا «إصلاح بيانات» كحل أول لمشكلة عرض.
- Compatibility Matrix إلزامية عند كل إصلاح يمس الشجرة.
- أي انحراف في القواعد يُعتبر خرقًا معماريًا يجب إغلاقه قبل الإصدار.

## ADR-006 — لا قبول بلا تطبيق متحقَّق

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

سياسة عامة لكل أنواع الاعتماد: لا حالة «مقبول / تم» بدون تطبيق متحقَّق على البيانات (طلبات، صور، زوجات، دمج، وأي اعتماد لاحق).

### Consequences

- `approved` بلا أثر في الشجرة = خطأ (`REQ-001`) وليس حالة نهائية مقبولة.
- معايير القبول وKPI تشمل نسبة نجاح التطبيق المتحقَّق = 100%.
- واجهات الاعتماد تعرض/تُغلق فقط بعد التحقق من الأثر.

## ADR-007 — حماية Patch 0 قبل أي إصلاح يمس البيانات

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

قبل أي Patch يمس البيانات: Backup كامل → Integrity Scan → تقرير محفوظ → تسجيل Schema/Data/Migration Version → خطة Rollback. لا Patch 1 بدون اكتمال Patch 0.

### Consequences

- كل Patch لاحق: تطبيق → Validation → Rollback جاهز.
- Migrations: Dry Run → تطبيق → تحقق.
- فشل التحقق يفعّل الاسترجاع؛ لا يُغلق البند بـ «تم» دون تحقق.

## ADR-008 — سياسة الكاش مربوطة بالأحداث والإصدارات

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-07 |

### Decision

تحديث ومسح الكاش (Web / Mobile / Widget) يُربطان بـ Event Bus وبـ Data/Migration Version. لا اعتماد على TTL وحده لضمان اتساق الشجرة أو الأخبار.

### Consequences

- خبر منتهٍ ظاهر في كاش/ودجت = خرق (`NEWS-001` / `NEWS-002`).
- تغيير Data/Migration Version يستوجب refresh/مسح صريح حسب السطح.
- Widget يعيد بناء Timeline صراحة بعد أحداث الأخبار ذات الصلة.

## ADR-009 — DateEngine موحّد للتواريخ التجارية (هجري ⇄ ميلادي)

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-08 |
| **المكتبة** | [`assets/js/modules/date-engine.js`](../assets/js/modules/date-engine.js) |

### Decision

كل **تواريخ الأعمال** (ميلاد، وفاة، مناسبة، انتهاء تصويت، …) تمر عبر مكتبة **DateEngine** الموحّدة:

1. **تحويل تلقائي** هجري ⇄ ميلادي — بلا زر «تحويل».
2. **صيغ مقبولة:** `1448/2/25`، `1448-2-25`، أرقام عربية/هندية، وما يعادلها ميلادياً.
3. **تطبيع الأرقام** (Arabic/Indic → Latin) قبل أي parse.
4. **تحقق حي** أثناء الكتابة (`bindLiveValidation`).
5. **تخزين مزدوج متزامن** عند توفر الأعمدة: `*_g` و `*_h` (مثل `birth_date_g` / `birth_date_h`، ولاحقاً `poll_end_g` / `poll_end_h`، …).
6. **منع القيم الهجرية** في أعمدة الطابع الزمني الميلادي (`timestamptz` / `datetime`) — مثال معروف: `family_polls.ends_at = 1448-…` يُرفض برمز `DATE-002`.
7. **يُمنع** استخدام `new Date(...)` مباشرة لتواريخ الأعمال خارج DateEngine (عرض «الآن» للواجهة فقط مسموح بحذر).

### Migration path (لا هجرة مخطط كاملة في هذه الجولة)

| المرحلة | المحتوى |
|---------|---------|
| **الآن** | المكتبة + ADR + حارس `ends_at` في إدارة التصويت (مستهلك أول) — **بنية تحتية** في الخارطة (ليس ملاحظة جانبية) |
| **لاحقاً** | ربط نماذج الميلاد/الوفاة/المناسبات بـ `toSyncedPair` (دين تقني TD-1) |
| **مخطط DB** | إضافة/توحيد أعمدة `*_g` / `*_h` حيث ينقص الزوج؛ الإبقاء على `ends_at` ميلادياً للطابع الزمني مع زوج اختياري للعرض |

لا تُرحَّل كل الجداول إلى `*_g`/`*_h` في هذه الجولة. قواعد الانحدار في الخارطة تلزم DateEngine لكل تواريخ الأعمال (R-5).

### Consequences

- أي تاريخ أعمال جديد يُكتب عبر DateEngine أو يُرفض كخرق معماري.
- حقول timestamp ميلادية ترفض سنوات النطاق الهجري (~1200–1700) قبل التخزين.
- رموز خطأ: `DATE-001` (غير قابل للتحليل)، `DATE-002` (هجري في عمود ميلادي)، `DATE-003` (خارج النطاق)، `DATE-004` (ناقص أثناء الكتابة).

## ADR-010 — Workflow Engine طبقة مستقلة عن الواجهات

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-08 |
| **المواصفة** | [`docs/WORKFLOW-SPECIFICATION-v1.md`](./WORKFLOW-SPECIFICATION-v1.md) |

### Decision

**Workflow Engine** طبقة معمارية **مستقلة بالكامل** — ليست جزءًا من Delegate Workspace ولا Admin UI ولا Visitor Portal.

| الطبقة | تقرر |
|--------|------|
| **Delegates v2** | من لديه صلاحية (دور · فرع · عمليات) |
| **Workflow Engine** | ماذا يحدث للطلب (إنشاء · تعيين · انتقال · إشعار · Audit · deep link) — بلا معرفة بشكل الشاشة |
| **Delegate / Admin Workspaces** | كيف يُعرض العمل أو تُراقب التدفقات — تستدعي المحرك فقط |

كل أنواع الطلبات (`tree` / `event` / `memory` / `special_card` / مستقبلًا) تمر بنفس عُقد المحرك؛ الفرق = **Request Type** فقط.

### Consequences

- لا منطق حالات أو اعتماد داخل ملفات الواجهة.
- أي إشعار من انتقال حالة عبر المحرك — لا من زر/شاشة.
- قبل تنفيذ Delegate Workspace: مواصفة السير معتمدة + أساس المحرك.
- قاعدة بوابة الميزة في الخارطة ملزمة قبل كود أي ميزة جديدة.

## ADR-011 — دستور المنصة + محاذاة المراحل + SSOT + Zero Duplicate Logic

| الحقل | القيمة |
|--------|--------|
| **Status** | Accepted |
| **التاريخ** | 2026-08-08 |
| **الدستور** | [`PLATFORM-PRINCIPLES.md`](./PLATFORM-PRINCIPLES.md) · [`PRODUCT-LANGUAGE.md`](./PRODUCT-LANGUAGE.md) · [`WORKFLOW-SPECIFICATION-v1.md`](./WORKFLOW-SPECIFICATION-v1.md) · [`REQUEST-CATALOG.md`](./REQUEST-CATALOG.md) |
| **الخارطة** | [`ENGINEERING-ROADMAP.md`](./ENGINEERING-ROADMAP.md) |

### Decision

1. **دستور المنصة** أربع وثائق رسمية منفصلة عن الخارطة:
   - لغة المنتج · مواصفة السير · فهرس النوايا · مبادئ المنصة  
   - Roadmap = **ماذا نبني؟** · Constitution = **كيف نفكر / ما يُمنع؟**

2. **الترتيب الكانوني المحدَّث** (بعد إغلاق Delegates v2):  
   **0 Product Foundation** → **1 Workflow Engine** → **2 Request Experience** → **3 Delegate Workspace** → **4 Admin UX** → **5 Family Engine Alignment**  
   المرحلة 5 = **مواءمة** خدمات موجودة (توحيد الدخول · منع الكتابة خارج Workflow · إزالة التكرار) — **ليست** إعادة بناء.

3. **Single Source of Truth (SSOT):** كل معلومة من مصدر واحد — حالة الطلب ← Workflow · صلاحية المندوب ← Delegates · الشخص ← Family Engine · الأخبار ← Events · الذكريات ← Memory.

4. **Zero Duplicate Logic:** أي تحقق/قاعدة يحتاجها أكثر من دور تُكتب مرة واحدة في المحرك أو الخدمة — لا نسخ في صفحات الواجهة.

### Consequences

- أي عملية جديدة للمستخدم تمر أولًا عبر [`REQUEST-CATALOG.md`](./REQUEST-CATALOG.md).
- شاشات جديدة تُرفض إن خالفت Human First / No Database Thinking ([`PRODUCT-LANGUAGE.md`](./PRODUCT-LANGUAGE.md)).
- مسارات كتابة UI→Service لعمليات الفهرس = خرق دستوري (إلى جانب ADR-010).
- تكرار منطق الأعمال بين الزائر/المندوب/الإدارة = خرق Zero Duplicate Logic.

## ملخص سريع (لا يُكسر)

1. الهوية = `person_id`  
2. لا ربط بالاسم عند الكتابة  
3. Event Bus = مصدر أحداث المجال بعد الاعتماد  
4. Health Center = مرجع صحة البيانات  
5. Tree Engine واحد عبر المنصات  
6. لا قبول بلا تطبيق متحقَّق  
7. Patch 0 حماية قبل أي إصلاح بيانات  
8. الكاش يتبع الأحداث والإصدارات  
9. DateEngine موحّد — لا `new Date()` لتواريخ الأعمال؛ لا هجري في timestamp ميلادي  
10. **Workflow Engine طبقة مستقلة** — بلا UI؛ نفس العُقد لكل نوع طلب؛ الواجهات بلا منطق أعمال  
11. **دستور المنصة** — أربع وثائق · SSOT · Zero Duplicate Logic · Family Engine Alignment · مراحل 0→5  

### إدارة المشروع (2026-08-08)

خارطة الطريق الرسمية [`ENGINEERING-ROADMAP.md`](./ENGINEERING-ROADMAP.md) هي وثيقة **إدارة مشروع** (ماذا نبني). دستور المنصة (أربع وثائق) يحدّد كيف نفكر وما يُمنع. الترتيب الكانوني: إغلاق **Delegates v2** → **Product Foundation** → **Workflow Engine** → **Request Experience** → **Delegate Workspace** → **Admin UX** → **Family Engine Alignment**. نموذج حالات 🟢🟡🔵⚪⬛، ثلاثة برامج، Tree Engine v2، DateEngine، دين تقني، وقواعد انحدار. المنصة = معرفة عائلية + سير اعتماد. هذا الملف (ADR) مصدر القرارات المعمارية المقفلَة فقط.
