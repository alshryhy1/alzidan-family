# تقرير حارس التكرار / الهوية الموحّد

**التاريخ:** 2026-08-09 (تحديث مسار الواجهة الحقيقي)  
**المستودع:** `alzidan-family`  
**النطاق:** طلبات الصفحة الرئيسية + مسارات الإنشاء المرتبطة (مناسبة / صحة / وفاة / ذكرى)

---

## 0) إصلاح حرج — مسار الواجهة الحقيقي (بعد إثبات المستخدم)

**الواقعة:** من الرئيسية → قدّم طلبًا → أضف فردًا موجودًا (مسار كامل + `person_id` / `parent_person_id` صحيحان) وصل الطلب إلى المراجعة. اختبارات الوحدة 16/16 **لا تُحسب** كإثبات لإصلاح الواجهة.

### الدالة التي سمحت بالخطأ

`submitAddPerson` في `assets/js/modules/request-experience.js` (زر `[data-rx-submit]` → «أرسل الطلب للمراجعة»).

الإنشاء الفعلي: `AlzidanHomeRequestCreate.create` → `insertApprovalRequest` → `approval_requests.insert`.

### لماذا لم يضرب الحارس المسار الحقيقي؟

1. `submitAddPerson` مرّر كتالوج الإخوة من RX بصيغة **camelCase** (`personId` / `parentPersonId`) مع `skipFetch: true`.
2. الحارس كان يقرأ فقط `person_id` / `parent_person_id` → فشل إثبات «نفس الابن تحت نفس الأب».
3. مسار «شخص آخر بنفس الاسم» وضع `different_person_same_name` فتجاوز مراجعة التشابه، والـ insert نجح رغم وجود الشخص.
4. البوابة الصلبة `findExistingChildUnderParent` قبل الإرسال كانت أُزيلت عند ربط الحارس.

### ما تغيّر

| ملف | التغيير |
|-----|---------|
| `dup-identity-guard.js` | قبول camelCase؛ حظر عند `person_id` في الحمولة؛ حظر تحت نفس الأب لا يتجاوزه «شخص آخر» |
| `request-experience.js` | إعادة بوابة الإخوة قبل أي insert؛ تطبيع الكتالوج؛ منع الإرسال عند اختيار هوية موجودة؛ فحص عند تأكيد الأب؛ `skipFetch: false` |
| `home-request-create.js` | دمج كتالوج DB الحي مع كتالوج الواجهة بدل استبداله عند `skipFetch: false` |
| `pages/index.html` | cache-bust `?v=20260809uifix1` |

### نتائج A/B/C/D المتوقعة (إثبات بمسار الكود + خطوات يدوية)

| | السيناريو | المتوقع |
|---|-----------|---------|
| **A** | ابن موجود تحت نفس الأب (اسم مطابق) | حظر قبل insert — رسالة عربية «موجود مسبقًا»؛ لا صف في `approval_requests` |
| **B** | اختيار من بوابة الهوية ثم «نعم، هذا هو المقصود» | شاشة «الشخص موجود» فقط — لا مراجعة ولا إرسال |
| **C** | «شخص آخر بنفس الاسم» لكن الابن موجود تحت **نفس** الأب | ما زال حظر (لا تجاوز) |
| **D** | نقر مزدوج على «أرسل» | إنشاء واحد فقط + رسالة تكرار |

**إثبات مسار الكود (بدون متصفح):**  
`submitAddPerson` → `findExistingChildUnderParent` return → `blockExistingPerson` **قبل** `Create.create`؛ وإن وصل: الحارس على كتالوج camelCase أو DB → `verdict=block` → `clearInflight` → **لا** `insertApprovalRequest`.  
اختبار انحدار: `npm run verify:dup-identity` يشمل كتالوج RX camelCase + `person_id` في الحمولة.

**يدويًا:** Hard refresh للرئيسية (`?v=20260809uifix1`) → أضف فردًا موجودًا تحت أبيه → يجب ألا يظهر «تم الإرسال».

## 1) السبب الجذري (الأصلي)

- منع التكرار كان **جزئيًا** ومحدودًا بمسار «أضف فردًا» في Request Experience (بوابة UI محلية).
- مسارات **المناسبة / الصحة / الوفاة / الذكرى** كانت تنشئ مباشرة بلا بوابة مشتركة.
- مبدأ المنتج: «تشابه النص لا يعني أن السجل مكرر، ووجود نفس الاسم لا يعني أنه نفس الشخص.»

---

## 2) أين تقع البوابة الموحّدة

| ملف | الدور |
|-----|--------|
| `assets/js/modules/dup-identity-guard.js` | تقييم نقي: `allow` / `block` / `review` + بصمة |
| `assets/js/modules/home-request-create.js` | **نقطة إنشاء وحيدة**: قفل نقر مزدوج → كتالوج → حارس → insert |
| `scripts/test-dup-identity-guard.js` | سيناريوهات + double-submit + انحدار واجهة camelCase |
| `npm run verify:dup-identity` | تشغيل الاختبار |

**الربط:** إضافة شخص: `request-experience.js` → `AlzidanHomeRequestCreate.create` (بعد بوابات RX الصلبة).

---

## 3) كيف يُثبت «نفس السجل» لإضافة شخص

| BLOCK | REVIEW | ALLOW |
|-------|--------|-------|
| نفس الاسم تحت نفس `parent_person_id` (أو مسار أب؛ يقبل camelCase من RX) | اسم مشابه تحت أب آخر بلا إقرار | لا تطابق / إقرار شخص مختلف **تحت أب مختلف** |
| `person_id` موجود في الحمولة (اختيار من الشجرة) | | |
| تأكيد المستخدم «نعم هذا هو المقصود» | | |

**صارم:** لا اعتماد على الاسم وحده؛ لا إنشاء هوية جديدة لشخص موجود؛ لا insert عند الحظر؛ النقر المزدوج يُمنع عند `create`.
