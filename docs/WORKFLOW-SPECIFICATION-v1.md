# Workflow Specification v1 — محرك سير الطلبات

**الحالة:** مسودة معتمدة للتخطيط (Draft v1) — تُنقَّح عند تنفيذ Workflow Engine v1  
**التاريخ:** 2026-08-08  
**المرجع:** [`ENGINEERING-ROADMAP.md`](./ENGINEERING-ROADMAP.md) · [`ADR.md`](./ADR.md) (ADR-010)  
**النطاق:** طبقة Workflow Engine فقط — بلا شكل واجهة (لا Delegate Workspace ولا Admin UI)

كل أنواع الطلبات تمر **بنفس عُقد المحرك**. الفرق الوحيد: **Request Type**.

---

## 1) أنواع الطلبات (Request Types)

| النوع (code) | العربية | ملاحظات |
|--------------|---------|---------|
| `tree` | شجرة / عضو | إضافة ابن، ربط، تعديل شجرة، … |
| `event` | مناسبة | |
| `memory` | ذكرى | |
| `special_card` | بطاقة خاصة | |
| *(future)* | أنواع لاحقة | تُضاف كـ type فقط — بلا آلة حالات جديدة |

---

## 2) حالات الطلب (Request States)

| الحالة (code) | العربية |
|---------------|---------|
| `submitted` | مُقدَّم |
| `assigned` | مُعيَّن |
| `in_review` | قيد المراجعة |
| `needs_changes` | يحتاج تعديلات |
| `approved` | معتمد |
| `applied` | مُطبَّق |
| `done` | مكتمل |
| `rejected` | مرفوض |

**سياسة:** لا تُغلق حالة `approved` كنجاح نهائي بلا `applied` متحقَّق (ADR-006). `done` بعد التحقق من الأثر.

---

## 3) الانتقالات المسموحة (Allowed Transitions)

```
submitted ──► assigned ──► in_review ──┬──► needs_changes ──► in_review
                                       ├──► approved ──► applied ──► done
                                       └──► rejected
```

| من | إلى | شرط مختصر |
|----|-----|-----------|
| `submitted` | `assigned` | تعيين مندوب/فرع وفق قواعد المحرك + صلاحية المندوب (Delegates v2) |
| `assigned` | `in_review` | المالك الحالي يبدأ المراجعة |
| `in_review` | `needs_changes` | طلب تعديل من المراجع |
| `needs_changes` | `in_review` | إعادة التقديم بعد التعديل |
| `in_review` | `approved` | قرار اعتماد (صلاحية العملية) |
| `approved` | `applied` | تطبيق متحقَّق على البيانات |
| `applied` | `done` | إغلاق بعد تحقق الأثر |
| `in_review` | `rejected` | قرار رفض |

انتقالات خارج الجدول = مرفوضة من المحرك (لا من الواجهة).

---

## 4) ملكية كل انتقال (Who owns)

| الانتقال | المالك التشغيلي | يتحقق المحرك من |
|----------|-----------------|-----------------|
| `submitted → assigned` | النظام / قواعد التعيين بالفرع | وجود مندوب مؤهل + فرع |
| `assigned → in_review` | المندوب المعيَّن (مالك الطلب) | المالك الحالي فقط |
| `in_review → needs_changes` | المندوب المالك | صلاحية المراجعة |
| `needs_changes → in_review` | مقدّم الطلب أو المندوب (حسب النوع) | الطلب ما زال مملوكًا لمسار التعديل |
| `in_review → approved` | المندوب المالك (أو مرحلة لاحقة لاحقًا) | صلاحية اعتماد النوع |
| `approved → applied` | المحرك / خدمة التطبيق | أثر بيانات متحقَّق |
| `applied → done` | المحرك | اكتمال التحقق + إغلاق |
| `in_review → rejected` | المندوب المالك | صلاحية الرفض |

**مبدأ:** لكل طلب مالك واحد واضح في كل لحظة. الإدارة تراقب؛ لا تستبدل المالك إلا بانتقال صريح عبر المحرك.

---

## 5) متى يُطلق الإشعار (Notifications)

الإشعار **من انتقال الحالة فقط** — ليس من زر أو شاشة.

| الانتقال | إشعار؟ | المستلم النموذجي |
|----------|--------|------------------|
| `submitted → assigned` | نعم | المندوب المعيَّن (+ إدارة اختياريًا) |
| `assigned → in_review` | لا (أو صامت تشغيلي) | — |
| `in_review → needs_changes` | نعم | مقدّم الطلب |
| `needs_changes → in_review` | نعم | المندوب المالك |
| `in_review → approved` | نعم | مقدّم الطلب |
| `approved → applied` | نعم (إن لزم تأكيد التطبيق) | مقدّم الطلب / مشتركو الحدث |
| `applied → done` | اختياري / ملخص | حسب النوع |
| `in_review → rejected` | نعم | مقدّم الطلب |

القنوات والقوالب = تفاصيل تنفيذ لاحقة؛ الحدث يصدر من المحرك (ويرتبط بـ Event Bus حيث ينطبق).

---

## 6) متى يُكتب Audit

| الحدث | يُكتب Audit؟ |
|-------|--------------|
| إنشاء الطلب (`submitted`) | نعم |
| كل انتقال حالة ناجح | نعم (من → إلى · فاعل · وقت · نوع الطلب · معرّف) |
| فشل انتقال (مرفوض بالصلاحية/القاعدة) | نعم (محاولة) |
| تطبيق بيانات (`approved → applied`) | نعم + مرجع الأثر |
| إسناد/إعادة إسناد المالك | نعم |

الواجهة لا تكتب Audit مباشرة — المحرك يكتب عند الانتقال.

---

## 7) حدود المسودة

- Multi-stage approval التفصيلي يُبنى فوق نفس العُقد لاحقًا (لا آلة موازية).
- Deep links: تُولَّد من المحرك عند التعيين/الانتقال ذي الصلة — بلا اعتماد على شكل الشاشة.
- أي نوع طلب جديد = صف في جدول الأنواع + نفس الانتقالات، لا محرك جديد.

**قبل تنفيذ Delegate Workspace:** هذه المواصفة (أو نسخة منقّحة صريحة) يجب أن تكون مرجع الحالات المعتمد.
