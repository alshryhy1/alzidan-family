## 1) أنواع الطلبات (Request Types)

الفهرس التشغيلي للنوايا: [`REQUEST-CATALOG.md`](./REQUEST-CATALOG.md). ملخص الأنواع:

| النوع (code) | نية المستخدم (عرض) | الخدمة بعد التطبيق |
|--------------|-------------------|---------------------|
| `tree_card` | أضف فردًا | Family Engine |
| `tree_edit` | صحح بيانات | Family Engine |
| `event_death` | أعلن وفاة | Family Engine |
| `event_marriage` | أعلن زواج | Family Engine |
| `memory_card` | شارك ذكرى | Memory Service |
| `special_card` | اطلب بطاقة | Cards |
| *(future)* | عبر الفهرس فقط | نفس العُقد — بلا آلة حالات جديدة |

أسماء المجموعات الأوسع (`tree` / `event` / `memory` / …) للتجميع والصلاحيات مقبولة داخليًا؛ **النوع المخزَّن للطلب** = صف الفهرس أعلاه.

## 2) حالات الطلب (Request States)

| الحالة (code) | النظام | المستخدم (افتراضي — انظر لغة المنتج) |
|---------------|--------|--------------------------------------|
| `submitted` | مُقدَّم | تم الإرسال |
| `assigned` | مُعيَّن | وصل للمندوب |
| `in_review` | قيد المراجعة | تحت المراجعة |
| `needs_changes` | يحتاج تعديل | نحتاج معلومة إضافية منك |
| `approved` | معتمد | تم قبول طلبك |
| `applied` | مُطبَّق | تمت إضافة البيانات |
| `done` | مكتمل | اكتمل |
| `rejected` | مرفوض | لم يُقبل |

**سياسة:** لا تُغلق حالة `approved` كنجاح نهائي بلا `applied` متحقَّق (ADR-006). `done` بعد التحقق من الأثر.

نصوص العرض الكاملة: [`PRODUCT-LANGUAGE.md`](./PRODUCT-LANGUAGE.md).

---

## 3) الانتقالات المسموحة (Allowed Transitions)

```
submitted ──► assigned ──► in_review ──┬──► needs_changes ──► in_review
                                       ├──► approved ──► applied ──► done
                                       └──► rejected
```

| من | إلى | شرط مختصر |
|----|-----|-----------|
| `submitted` | `assigned` | تعيين مندوب/فرع وفق قواعد المحرك + صلاحية المندوب (Delegates v2) |
| `assigned` | `in_review` | المالك الحالي يبدأ المراجعة |
| `in_review` | `needs_changes` | طلب تعديل من المراجع (سبب إلزامي) |
| `needs_changes` | `in_review` | إعادة التقديم بعد التعديل |
| `in_review` | `approved` | قرار اعتماد (صلاحية العملية) |
| `approved` | `applied` | تطبيق متحقَّق على البيانات عبر الخدمة من الفهرس |
| `applied` | `done` | إغلاق بعد تحقق الأثر |
| `in_review` | `rejected` | قرار رفض (سبب إلزامي) |

انتقالات خارج الجدول = مرفوضة من المحرك (لا من الواجهة).

---

## 4) التعيين والملكية (Assignment & Ownership)

| الانتقال | المالك التشغيلي | يتحقق المحرك من |
|----------|-----------------|-----------------|
| `submitted → assigned` | النظام / قواعد التعيين بالفرع | وجود مندوب مؤهل + فرع + صلاحية العملية (Delegates) |
| `assigned → in_review` | المندوب المعيَّن (مالك الطلب) | المالك الحالي فقط |
| `in_review → needs_changes` | المندوب المالك | صلاحية المراجعة + سبب |
| `needs_changes → in_review` | مقدّم الطلب أو المندوب (حسب النوع) | الطلب ما زال مملوكًا لمسار التعديل |
| `in_review → approved` | المندوب المالك (أو مرحلة لاحقة لاحقًا) | صلاحية اعتماد النوع |
| `approved → applied` | المحرك / خدمة التطبيق | أثر بيانات متحقَّق — **لا كتابة من الواجهة على الخدمة** |
| `applied → done` | المحرك | اكتمال التحقق + إغلاق |
| `in_review → rejected` | المندوب المالك | صلاحية الرفض + سبب |

**مبادئ:**

- لكل طلب **مالك واحد واضح في كل لحظة**.
- الإدارة تراقب؛ لا تستبدل المالك إلا بانتقال صريح عبر المحرك (إعادة إسناد = Audit).
- Workflow = **مصدر الحقيقة** لحالة الطلب وملكيته ([`PLATFORM-PRINCIPLES.md`](./PLATFORM-PRINCIPLES.md) — SSOT).

## 5) متى يُطلق الإشعار (Notifications)

الإشعار **من انتقال الحالة فقط** — ليس من زر أو شاشة.

| الانتقال | إشعار؟ | المستلم النموذجي |
|----------|--------|------------------|
| `submitted → assigned` | نعم | المندوب المعيَّن (+ إدارة اختياريًا) |
| `assigned → in_review` | لا (أو صامت تشغيلي) | — |
| `in_review → needs_changes` | نعم | مقدّم الطلب |
| `needs_changes → in_review` | نعم | المندوب المالك |
| `in_review → approved` | نعم | مقدّم الطلب |
| `approved → applied` | نعم (إن لزم تأكيد التطبيق) | مقدّم الطلب / مشتركو الحدث |
| `applied → done` | اختياري / ملخص | حسب النوع |
| `in_review → rejected` | نعم | مقدّم الطلب |

القنوات والقوالب = تفاصيل تنفيذ لاحقة؛ الحدث يصدر من المحرك (ويرتبط بـ Event Bus حيث ينطبق).  
نص الإشعار من عمود **المستخدم** في لغة المنتج.

---

## 6) متى يُكتب Audit

| الحدث | يُكتب Audit؟ |
|-------|--------------|
| إنشاء الطلب (`submitted`) | نعم |
| كل انتقال حالة ناجح | نعم (من → إلى · فاعل · وقت · نوع الطلب · معرّف) |
| فشل انتقال (مرفوض بالصلاحية/القاعدة) | نعم (محاولة) |
| تطبيق بيانات (`approved → applied`) | نعم + مرجع الأثر |
| إسناد/إعادة إسناد المالك | نعم |

الواجهة لا تكتب Audit مباشرة — المحرك يكتب عند الانتقال.

---

## 7) حدود المواصفة

- Multi-stage approval التفصيلي يُبنى فوق نفس العُقد لاحقًا (لا آلة موازية).
- Deep links: تُولَّد من المحرك عند التعيين/الانتقال ذي الصلة — بلا اعتماد على شكل الشاشة.
- أي نوع طلب جديد = صف في [`REQUEST-CATALOG.md`](./REQUEST-CATALOG.md) + نفس الانتقالات، لا محرك جديد.
- Request Experience وDelegate Workspace وAdmin UX **تستهلك** هذه المواصفة — لا تعرّف حالات خاصة بها.

**قبل تنفيذ Delegate Workspace / Request Experience كشاشات إنتاج:** هذه المواصفة (أو نسخة منقّحة صريحة) يجب أن تكون مرجع الحالات المعتمد، مع تجميد وثائق Product Foundation ذات الصلة.
