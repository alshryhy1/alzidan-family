# تقرير حارس التكرار / الهوية الموحّد

**التاريخ:** 2026-08-09  
**المستودع:** `alzidan-family`  
**النطاق:** طلبات الصفحة الرئيسية + مسارات الإنشاء المرتبطة (مناسبة / صحة / وفاة / ذكرى)

---

## 1) السبب الجذري

- منع التكرار كان **جزئيًا** ومحدودًا بمسار «أضف فردًا» في Request Experience (بوابة UI محلية: ابن تحت نفس الأب + تصادم اسم).
- مسارات **المناسبة / الصحة / الوفاة / الذكرى** كانت تُنشئ `approval_requests` أو `family_events` أو `memory_submit_item_v1` مباشرة من النماذج **بدون** بوابة هوية مشتركة.
- الاعتماد على **تشابه الاسم** أو تعطيل الزر في الواجهة فقط لا يثبت نفس الكيان، ولا يمنع النقر المزدوج عند نقطة الإنشاء.
- مبدأ المنتج: «تشابه النص لا يعني أن السجل مكرر، ووجود نفس الاسم لا يعني أنه نفس الشخص.»

---

## 2) تدقيق مسارات الرئيسية (قبل الإصلاح)

| النوع | أين يُنشأ | فحص الوجود سابقًا | ثغرة |
|------|-----------|-------------------|------|
| إضافة شخص `tree_card` | `request-experience.js` → `approval_requests` | بوابة أخ/أب محلية فقط | يمكن تجاوز المنطق إن تغيّر المسار؛ لا بوابة موحّدة |
| مناسبة سعيدة `event_card` | `event-submit.js` | لا يوجد | تكرار نفس المناسبة ممكن |
| صحة/مريض | مندوب `delegate-events-mgmt.js` (تُعرض في الرئيسية) | لا يوجد | تكرار نفس الحالة ممكن |
| وفاة | مندوب `delegate-events-mgmt.js` | لا يوجد | وفاة ثانية بلا ربط `person_id` |
| ذكرى | `memory/submit.js` → RPC | لا يوجد | ذكرى مطابقة ممكنة |
| صندوق/مؤسس `org_role` | `app.js` | خارج نطاق كيانات هذا الحارس | — |
| بطاقة شجرة قديمة | `app.js` (`data-tree-card-form`) | النموذج غير موجود في `index.html` حاليًا | مسار ميت |

**أنواع بلا حماية تكرار/هوية قبل هذا التغيير:** مناسبة، صحة، وفاة، ذكرى (+ ضعف توحيد مسار الإضافة).

| ملف | الدور |

**الربط:**

- صحة/وفاة/مناسبة (مندوب): `delegate-events-mgmt.js`
- ذكرى: `memory/submit.js`

## 4) كيف يُثبت «نفس السجل» لكل نوع

| النوع | BLOCK (نفس الكيان) | REVIEW (تشابه غير مؤكد) | ALLOW |
|------|---------------------|-------------------------|-------|
| إضافة شخص | نفس الاسم تحت نفس `parent_person_id` (أو مسار أب مطابق)، أو `person_id` موجود | نفس الاسم في الشجرة تحت أب آخر — بدون إقرار «شخص آخر» | لا تطابق / إقرار شخص مختلف بنفس الاسم |
| مناسبة | `type` + `person_id` + تاريخ (`date_label`/`event_date`) + فرع؛ أو عنوان+تاريخ بلا اسم وحده | عنوان/نوع متشابه بلا إثبات كامل | تاريخ أو شخص مختلف |
| صحة | نفس `person_id` + نفس نوع الحالة + (مستشفى أو حي/مدينة أو تاريخ) | نفس الشخص ونوع الحالة بلا حقول مكتملة | نوع حالة مختلف لنفس الشخص مسموح |
| وفاة | `person_id` عليه وفاة في الشجرة أو مناسبة death بنفس المعرف | اسم مشابه بلا `person_id` — **لا حظر بالاسم** | شخص مختلف بالمعرف |
| ذكرى | نفس `person_id` + عنوان + نوع (+ تاريخ إن وُجد) | عنوان مشابه لنفس الشخص | عنوان مختلف لنفس الشخص مسموح |

**قواعد صارمة مطبّقة:** لا اعتماد على الاسم وحده؛ لا إنشاء `person_id` جديد لشخص موجود؛ لا دمج/حذف/تعديل تلقائي لبيانات الشجرة؛ التشابه → مراجعة وليس حظرًا أعمى.

---

## 5) التشابه غير المؤكد

- الحكم `review` / `needsReview`.
- لا auto-merge.
- في RX: واجهة اختيار «موجود» vs «شخص آخر بنفس الاسم».
- في النماذج العامة/المندوب: رسالة عربية تطلب مراجعة الحقول أو إقرار الاختلاف (`acknowledgeReview` / `different_person_same_name`) قبل الإنشاء.

## 7) هل لزم تغيير قاعدة البيانات؟

**لا.** لم تُطبَّق migrations ولم يُنفَّذ SQL.

الحماية الحالية: طبقة تطبيق عند نقطة الإنشاء + قفل بصمة في الجلسة.

**اختياري لاحقًا (COPY-ME فقط إذا رُغب بفرض خادم):**  
قيد/دالة RPC ترفض إدراج `approval_requests` / مناسبة / ذكرى عند تطابق بصمة كيان — لم يُكتب ولم يُطبَّق في هذا التغيير احترامًا لسياسة «لا تنفّذ SQL بنفسك».
