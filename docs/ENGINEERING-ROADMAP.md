# عائلة الزيدان — Engineering Roadmap (مرجع رسمي)

**الحالة:** معتمد رسميًا — 10/10  
**التاريخ:** 2026-08-07  
**آخر تحديث تخطيط:** 2026-08-07 — تصحيح المسار: **Admin Redesign → Delegates v2 → Admin UX → ثم UX الموبايل** (رفض قفز UX الموبايل قبل الإدارة)  
**القرارات المعمارية المقفلَة:** [`docs/ADR.md`](./ADR.md)

وثيقة التنفيذ الهندسية الرسمية لمشروع عائلة الزيدان. تعالج جذور المشاكل حسب طبقات النظام، وليست قائمة مزايا فقط.

**سياسة عامة للمشروع:** لا «مقبول / تم» بلا تطبيق متحقَّق — على الطلبات، الصور، الزوجات، الدمج، وأي اعتماد لاحق.

**الهدف التنفيذي التالي:** **المرحلة 1 — إعادة تصميم الإدارة (Admin Redesign)** بما فيها معمارية **الموديولات**. لا يبدأ التنفيذ إلا بقول المستخدم «ابدأ». UX الموبايل **بعد** مراحل الإدارة فقط.

## 2) Canonical Person Identity

```
person_id          ← هوية مستقرة
    ↓
Node Path          ← موقع كانوني في الشجرة
    ↓
Display Name       ← للعرض
    ↓
Search Name        ← للبحث/التطبيع
```

كل كتابة تمر بـ `person_id`. ممنوع الربط الغامض بالاسم (`limit(1)` / `min()` على تطابق متعدد).

## 3) Versioning للبيانات

يظهر في Patch 0 وHealth Center وDiagnostics:

| الحقل | المعنى |
|--------|--------|
| **Schema Version** | إصدار هيكل الجداول/القيود |
| **Data Version** | إصدار منطق البيانات / قواعد الهوية |
| **Migration Version** | آخر migration script طُبّق بنجاح |

الغرض: معرفة هل البيانات القديمة مرّت بالإصلاح قبل تشخيص أي عطل جديد.

## 5) Architecture Decisions (ADR)

قرارات معمارية **مقفلة** — ليست اقتراحات. التفاصيل الكاملة في [`docs/ADR.md`](./ADR.md).

| ADR | القرار |
|-----|--------|
| ADR-001 | الهوية تعتمد على `person_id` (Canonical Person Identity) |
| ADR-002 | ممنوع الربط بالاسم عند الكتابة |
| ADR-003 | Event Bus هو المصدر الوحيد لأحداث المجال بعد الاعتماد |
| ADR-004 | Health Center مرجع صحة البيانات (Diagnostics للتفاصيل التقنية) |
| ADR-005 | محرك شجرة واحد — Web / Admin / Mobile بلا محركات متباعدة |
| ADR-006 | لا قبول بلا تطبيق متحقَّق (سياسة عامة) |
| ADR-007 | حماية Patch 0 قبل أي إصلاح يمس البيانات |
| ADR-008 | سياسة الكاش مربوطة بالأحداث وإصدارات البيانات |

أي خرق لهذه القرارات يُوقف الإغلاق حتى يُصحَّح أو يُوثَّق ADR جديد صراحةً.

## 6) Patch 0 — حماية البيانات

| خطوة | التفاصيل |
|------|----------|
| Backup كامل | جداول الشجرة، الطلبات، الزوجات، الأخبار، … |
| Integrity Scan | تكرارات، أبناء بلا أب، `parent_person_id`، زوجات بلا زوج، cycles، طلبات مقبولة بلا أثر |
| تقرير | يُحفظ ويُراجع قبل Patch 1 |
| تسجيل Versioning | Schema / Data / Migration |
| **Rollback Plan** | طريقة الاسترجاع موثّقة ومجرَّبة على نسخة الاختبار إن أمكن |
| بوابة | لا Patch 1 بدون اكتمال ما سبق |

### قالب كل Patch لاحق

```
تطبيق الإصلاح
    ↓
Validation (معايير القبول + KPI جزئية)
    ↓
إن فشل → Rollback إلى Backup / Migration السابق
```

## 9) Event Bus

```
اعتماد (ابن / زوجة / صورة / دمج / تعديل)
    ↓
حدث واحد موثّق (RequestApplied / PersonLinked / …)
    ↓
الشجرة · الويب · الموبايل · الودجت · الكاش · الإشعارات
```

لا تحديث صامت في مسار واحد مع ترك الباقي.

## 10) Cache Policy

| السطح | متى Refresh | متى مسح الكاش | ملاحظات |
|--------|-------------|---------------|---------|
| **Web** | بعد اعتماد / تعديل شجرة / تغيير أخبار | عند فشل تطابق Version | |
| **Mobile** | فتح الشجرة / سحب للتحديث / بعد حدث | عند تغيير Data/Migration Version | |
| **Widget** | Timeline / App Group / بعد حدث أخبار | مسح عند انتهاء خبر أو فشل فلتر | إعادة بناء Timeline صراحة |

## 12) Health Center vs Diagnostics

| | **Health Center** | **Diagnostics** |
|--|-------------------|-----------------|
| الجمهور | المدير | الصيانة / المطوّر |
| الحالة | ✅ **مكتمل** (أساس قراءة فقط في الإدارة) | لاحقًا ضمن موديولات الإدارة |
| يعرض | المشاكل (أبناء بلا أب، تكرار، طلبات عالقة، أخبار منتهية، روابط مكسورة…) | التفاصيل التقنية |
| أمثلة | عدد المشاكل + روابط إصلاح | آخر Sync، آخر Migration، آخر Build، آخر Widget Refresh، آخر Backup، آخر Scan، الإصدارات الثلاث |

Health Center يبقى مركزًا مستقلًا ضمن معمارية الموديولات في Phase 1 (§17). Diagnostics بعد ذلك في خارطة المنتج.

## 13) Data Integrity Engine

محرك **دائم** (ليس تقرير Patch 0 فقط): أبناء بلا أب، أب بلا فرع، `parent_person_id`، `person_id` مكرر، cycles، زوجة بلا زوج، أبناء خارج الفرع / بشخصين، `approved` بلا أثر، أخبار منتهية ظاهرة. يغذي Health Center.

**للتخطيط:** مسار Integrity قراءة فقط = ✅ مغلق. أي إصلاح كتابة لاحق = dry-run + موافقة صريحة.

## 17) مراحل الإدارة — الترتيب المعتمد (التالي)

**بدء التنفيذ:** عند قول المستخدم «ابدأ» فقط — المرحلة 1 أولًا.  
**صريح:** اقتراح «UX موبايل أولًا» **مرفوض**؛ لا يُقفز فوق هذه المراحل.

### المرحلة 1 — Admin Redesign ← التالي

- لوحة تحكم جديدة
- إعادة تنظيم كل الأقسام
- إزالة التكدّس الحالي (صفحة طويلة مزدحمة)
- توحيد مراكز الإدارة
- كل عملية عبر **Workflow** واضح
- **معمارية الموديولات (Modules):** مراكز مستقلة بدل صفحة واحدةحدة، منها:
  - إدارة الشجرة
  - إدارة الأعضاء
  - إدارة المناسبات
  - إدارة الذكريات
  - إدارة المندوبين
  - مركز الصحة (Health Center) — موجود كأساس ✅ ويُدمَج كموديول
  - مركز السجل (Audit)
  - …وغيرها حسب الحاجة

### المرحلة 2 — Delegates v2

- صلاحيات حسب الدور (Role-based)
- صلاحيات حسب الفرع (Branch-based)
- صلاحيات حسب نوع العملية
- اعتماد متعدد المراحل (Multi-stage approval)
- سجل تدقيق كامل (Full Audit Trail)
- تفعيل / تعطيل المندوبين

### المرحلة 3 — Admin UX

- بحث إداري كامل
- فلاتر متقدمة
- عمليات جماعية (Bulk)
- مركز استيراد / تصدير
- مركز النسخ الاحتياطي (Backup)
- مركز المهام / الصيانة
